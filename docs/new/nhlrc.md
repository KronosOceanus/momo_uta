# nhlrc：带振假名的歌词文件

> 读者：要改歌词读写、导入导出、标注落盘的人。
> 定位：**格式规范 + 读写规则**，自成一体：先讲 LRC 是什么，再讲我们多加了什么。
> 不依赖任何其它文档；代码位置只写模块/函数名，不写行号。

## 0. 三十秒版本

```text
.nhlrc = 一份普通 LRC 歌词 + 文件末尾一段 JSON（振假名标注）

普通 LRC 播放器读到前半段，行为不变；
我们的播放器读到 "#NHLRC 1" 之后，把每个汉字该读什么也读出来。
```

```text
[ti:君の名前]
[00:12.34]君の名前を呼んで
[00:16.02]ずっと覚えている

#NHLRC 1
{
 "v": 1,
 "gen": "nihonco 0.1",
 "body": "03f12d07",
 "lines": [
  {"i": 0, "h": "d6bdabed", "seg": [["君","きみ","AB"],["の",null,null],["名前","なまえ","A"],["を呼んで",null,null]]},
  {"i": 1, "h": "0201bf8f", "seg": [["ずっと",null,null],["覚","おぼ","A"],["えている",null,null]]}
 ]
}
```

```text
它解决的问题：
  LRC 只有"时间 + 文本"，表达不了"哪个汉字读什么"。
  振假名（ruby）是日语歌词练习的核心信息，必须能存下来、能校验、能被别的工具忽略。
```

## 1. 为什么需要新格式

```text
LRC 的能力边界：
  [mm:ss.xx]一行文本        —— 时间 + 文本
  [ar:][ti:][offset:] 等    —— 元数据标签
  没有"字符级读音"的位置
```

三种"不改格式"的存法都试过，各有硬伤：

```text
① 读音写进正文：  君(きみ)の名前(なまえ)
   → 正文不再是正常歌词，别的播放器会显示括号注音，打轴也更容易错位

② 正文夹自定义符号： 君{きみ}の
   → 同上，且不同工具会当普通字符处理，搜索/排序全乱

③ 纯 JSON 文件：  {"lrc": "...", "ruby": [...]}
   → 人类不可读、git diff 难看、普通播放器完全打不开
```

```text
结论：
  正文保持 100% 合法 LRC（兼容、可退化），
  读音放在文件末尾的一段 JSON 里（人类可读、可扩展、普通播放器会当无时间戳行忽略）。
```

## 2. 文件结构

```text
<LRC 正文>
<空行>
#NHLRC 1
<JSON 尾部>
```

```text
硬规则：
  · 标记行之前的所有内容，必须是一份完整的、合法的 LRC
  · 标记行形如 #NHLRC <版本号>；写入方固定写 "#NHLRC 1"
    读取方只要求行首（去空白后）以 "#NHLRC" 开头
  · 标记之后是 JSON 对象；JSON 解析失败 → 整个尾部作废（当纯 LRC 处理）
  · 文件编码 UTF-8，换行 \n
```

```text
没有标注时，文件就是纯 LRC（不写标记、不写尾部）。
所以 .nhlrc 是 .lrc 的超集：任何 .lrc 都可以原样当 .nhlrc 读。
```

### 2.1 正文解析器接受的写法

```text
[mm:ss.xx]文本            标准
[mm:ss]文本               无小数
[mm:ss.xx-1]文本          KTV 变体（尾部 -1 忽略）
{"t":毫秒,"c":[{"tx":"…"}]}  网易云逐行 JSON（逐行解析，不是整文件 JSON）
[ar:][ti:][al:][by:][offset:][length:][re:][ve:][la:][id:][tool:]
                          元数据标签：不进正文行，单独保留
其余非空行                 当作"未打点草稿行"保留
```

```text
不支持的写法（会被当成草稿文本，不会被理解）：
  · 增强型 LRC：<00:12.34>逐字标签
  · 一行多个时间戳：[00:12.34][00:15.67]同一句
```

## 3. 尾部字段

```json
{
 "v": 1,
 "gen": "nihonco 0.1",
 "body": "03f12d07",
 "lines": [
  {"i": 0, "h": "d6bdabed", "seg": [["君","きみ","AB"],["の",null,null]]}
 ]
}
```

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `v` | int | 是 | 格式版本，当前 `1`；只增不改 |
| `gen` | string | 否 | 生成器标识（排查问题用，不参与校验） |
| `body` | string | 否 | 整篇正文的哈希（sha1 前 8 位十六进制）：校验快路径，见 §4 |
| `lines` | array | 是 | 每行一条标注；按 `i` 升序写 |
| `i` | int | 是 | 正文行序号（从 0 开始） |
| `h` | string | 是 | 该行文本的哈希（sha1 前 8 位） |
| `seg` | array | 是 | 片段数组，见下 |

### 3.1 `seg` 片段

```text
seg = [[base, ruby, level], ...]        // 每个元素是三元组

base   该片段的原文（必须拼起来等于整行文本）
ruby   平假名读音；null = 这段不注音（假名、标点、送り仮名）
level  A / AB / B / C / null
```

```text
例：君の名前を呼んで
  [["君","きみ","AB"], ["の",null,null], ["名前","なまえ","A"], ["を呼んで",null,null]]

规范：
  · base 拼接必须严格等于正文行文本（含标点、空格）
  · ruby 只能是平假名（可以带 ー）
  · level=K 等价于 ruby=null；写入方对无读音片段写 null 更省
```

### 3.2 "一行"怎么数

```text
i 数的是正文解析后的行序号，规则：
  · 跳过空行
  · 跳过元数据标签（[ar:] 这类，它们不进 lines）
  · 保留未打点草稿行（t=null 也是行）
  · 保留带时间戳的普通行（包括"作词 : X"这种被当普通行的信息行）
```

```text
所以外部编辑正文时：
  删一行 / 加一行 / 调换顺序 → 后面的 i 全部错位 → 标注会失效（见 §4）
```

## 4. 校验与失效

读取时 `lrc_doc.annotations_for(lines, tail, strict)` 对每条标注做三道检查：

```text
① 下标：0 <= i < len(lines)，否则丢弃
② 拼接：seg 里 base 拼起来必须等于该行文本，否则丢弃
③ 哈希：strict 时 h 必须等于该行文本哈希，否则丢弃
```

### 4.1 `body` 哈希的作用：快路径

```text
body = sha1(整篇正文)[:8]

读取时：
  body 与当前正文的哈希一致
      → 正文没动过 → 跳过 ③（不再逐行比 h），仍然做 ① ②
  body 缺失 / 不一致
      → 走逐行 ③（每一行按 h 判断）
```

```text
为什么两套都要：
  · 逐行哈希能精确定位"哪一行被改了"（局部失效）
  · body 哈希能一次判断"整篇没动"，省掉逐行比较（快路径）
  · 即使 body 一致，仍然校验拼接：尾部被外部工具改坏时不会错位显示
```

### 4.2 三种失效场景

| 场景 | 结果 | 恢复方式 |
|---|---|---|
| 改了一行的文字 | 该行 h 对不上 → 该行标注作废，其它行保留 | 保存该行时重新注音 |
| 删掉/插入一行 | 后面所有 i 错位 → 逐行 h 大量对不上 | 重新打开时按新正文重新注音 |
| 尾部 JSON 坏了 | 尾部整体作废 → 当纯 LRC 读（没有标注） | 重新注音 / 保存 |

```text
作废的行不会"错位显示"：那一行按普通歌词显示，没有 ruby。
```

## 5. 读写规则

### 5.1 加载

```text
文件优先级：
  1) 同目录同名 .nhlrc
  2) 同目录同名 .lrc
  3) 歌词缓存（没有本地文件时）

特殊情况：
  · .nhlrc 的正文为空（0 行文本）而 .lrc 有内容 → 回退读 .lrc
    （防止误存出空壳文件把有内容的歌词盖住）
  · .nhlrc 正文为空且没有 .lrc → 没有歌词（触发懒匹配）
```

```text
标注来源：
  · 有 .nhlrc → 按 §4 校验尾部
  · 只有 .lrc → 没有标注（打开后自动注音，再落盘）
  · 只有缓存 → 缓存里的 nhlrc_annotations 字段（同样的三元组结构）
```

### 5.2 保存

```text
输入：编辑器里的行（t + 文本）
步骤：
  ① 读旧文件，拿 metadata（[ti:] 这类标签）与旧标注
  ② 逐行决定标注：
       新文本 == 旧文本（拼接相同） → 沿用旧标注
       否则                         → 重新注音
  ③ 生成正文：行 + 元数据按原位置插回
  ④ 生成尾部：render_nhlrc(行, 元数据, 标注)
  ⑤ 写文件（覆盖）
```

```text
保护：
  · 没有非空歌词行 → 拒绝保存（不写空文件）
  · 首次写 .nhlrc 前，把现有的 .nhlrc 或 .lrc 备份成 .nhlrc.bak
    （之后再保存不会覆盖 .bak）
  · 清除"恢复最初"用 .nhlrc.bak；没有它时兼容读旧的 .lrc.bak
```

### 5.3 自动落盘

```text
有本地歌词文件（.lrc 或 .nhlrc）的歌：
  打开时如果发现没有 .nhlrc（或标注缺行）→ 注音后自动写一份 .nhlrc

纯缓存歌曲（没有本地歌词文件）：
  不往音乐目录写文件；标注写进歌词缓存的 nhlrc_annotations 字段
```

```text
自动落盘只在"正文有非空歌词行"时发生；空歌词不写盘。
```

### 5.4 缓存里的标注

```text
歌词缓存 JSON 里可能带：
  "nhlrc_annotations": {"0": [["君","きみ","A"], …], "1": …}
结构 = 尾部 lines 的 i → seg（不带 h；读取时按拼接校验）
用途 = 导入 nhlrc 时保留读音，不必重新注音
```

## 6. 导入 / 导出

### 6.1 导入音频（歌单右键「导入音乐」）

```text
规则：
  · 同名词曲文件：.nhlrc 优先于 .lrc
  · 读到 .nhlrc → 正文进缓存，标注也一起带进缓存
  · 只有音频没有歌词 → 进歌单，标记"待匹配"
  · 歌词少于 3 行 → 视为没有可用歌词
```

```text
导入只读源文件，不改源文件、不往源目录写东西。
```

### 6.2 导入歌词（LRC 工具栏「导入」）

```text
接受 .lrc / .nhlrc。
  · 只取正文，标注清空（旧读音不沿用）
  · 覆盖前备份当前 .nhlrc
  · 首次覆盖不产生空文件（文件空 → 报错）
```

### 6.3 导出（LRC 工具栏「导出」）

```text
默认文件名：<歌名>.nhlrc
对话框里把扩展名改成 .lrc：
  → 只写正文（纯 LRC，不含尾部）
否则：
  → 写完整 .nhlrc（正文 + 尾部）
```

```text
导出的尾部是按当前内容重新生成的：
  · 未知的尾部字段会丢（只保留 v/gen/body/lines）
  · 需要保留的自定义信息请放在正文元数据标签里
```

### 6.4 文件命名

```text
与音频同目录、同 stem：
  song.flac   → song.nhlrc
  song.mp3    → song.nhlrc
```

## 7. 与普通 LRC 的兼容性

```text
能保证的：
  · 前半段（标记行之前）对任何 LRC 播放器都是合法文件
  · 把 .nhlrc 改名成 .lrc 也能播（尾部是无时间戳行）
  · 没有标注时，文件本来就是纯 LRC
```

```text
不能保证的：
  · 尾部是"无时间戳的非空行"，多数播放器忽略；
    少数播放器会把它们当歌词显示（会看到 JSON 文本）
  · 草稿行（没有时间戳的歌词）同样各播放器行为不同
  · 增强型逐字时间、多时间戳不支持（见 §2.1）
```

```text
如果只想要"绝对兼容"：用「导出」存成 .lrc（只有正文）。
```

## 8. 演进规则

```text
· 正文永远不许为了新功能而变脏（不能把标注塞进正文）
· 尾部是唯一扩展点；读取方必须忽略不认识的字段
· v 只增不改：新增能力时 v+1，旧读取方遇到更高 v 时可以：
    a) 按已知字段尽力读（推荐）
    b) 整份当纯 LRC 读（保守）
· 未来可能加的字段（示例，不是承诺）：
    lines[].zh      该行翻译
    lines[].note    人工备注
    layers          其它读音体系（罗马音/键位一般不存，由假名推导）
```

## 9. 完整示例与流程

### 9.1 一个真实文件

```text
[ti:君の名前]
[ar:テスト]
[00:12.34]君の名前を呼んで
[00:16.02]ずっと覚えている
[00:20.10]また会おう

#NHLRC 1
{
 "v": 1,
 "gen": "nihonco 0.1",
 "body": "03f12d07",
 "lines": [
  {"i": 0, "h": "d6bdabed", "seg": [["君","きみ","AB"],["の",null,null],["名前","なまえ","A"],["を呼んで",null,null]]},
  {"i": 1, "h": "0201bf8f", "seg": [["ずっと",null,null],["覚","おぼ","A"],["えている",null,null]]},
  {"i": 2, "h": "0c3d2074", "seg": [["また",null,null],["会","あ","A"],["おう",null,null]]}
 ]
}
```

```text
核对：
  body     = sha1("[ti:…]\n[ar:…]\n[00:12.34]…\n…\n")[:8] = 03f12d07
  i=0 h    = sha1("君の名前を呼んで")[:8]                  = d6bdabed
  i=1 h    = sha1("ずっと覚えている")[:8]                  = 0201bf8f
  i=2 h    = sha1("また会おう")[:8]                        = 0c3d2074
```

### 9.2 写流程

```text
编辑器行（t + 文本）
   │
   ├─ render(lines, metadata) ────────────────► 正文
   │
   ├─ 逐行：文本没变 → 旧标注；变了 → 重新注音
   │
   └─ render_nhlrc(lines, metadata, 标注) ────► 正文 + 尾部
                                                │
                            备份（首次）.nhlrc.bak
                                                │
                                              写盘
```

### 9.3 读流程

```text
读文件
  │
  ├─ 找 "#NHLRC" 标记 → 拆成（正文, 尾部 JSON）
  │
  ├─ 解析正文 → lines + metadata
  │
  ├─ 校验尾部：body 快路径 + 下标 + 拼接（+ 必要时逐行 h）
  │
  └─ 交给上层：lines（带 ruby）+ annotations（按 i 对齐）
```

## 10. 边界与已知限制

```text
① 行级哈希，不是字符级
   一行改一个字，整行标注作废（这是有意的：避免错位）

② 下标映射依赖正文行顺序
   外部工具重排/删除行 → 后面大量失效；重新注音即可恢复

③ 尾部会被重写
   保存时按当前内容重新生成，未知字段丢失（见 §6.3）

④ 不做压缩/加密
   4 分钟、40 行的歌，尾部大小与正文同量级（一行一条之后）

⑤ 只支持 UTF-8
   读取时容忍首行 BOM；写入不带 BOM

⑥ 正文解析能力有限
   增强型逐字时间、一行多时间戳不支持；遇到会当草稿文本

⑦ 空文件保护
   没有非空歌词行时：不自动写、保存被拒、打开视为"没有歌词"
```

## 12. 术语表

| 词 | 意思 |
|---|---|
| LRC | 最常见的歌词文本格式：`[mm:ss.xx]文本` |
| 正文（body） | 标记行之前的 LRC 部分 |
| 尾部（tail） | `#NHLRC` 之后的 JSON |
| 振假名（ruby） | 标在汉字上的读音 |
| 片段（segment） | 连续原文 + 可选读音的最小单位 |
| 草稿行 | 还没打时间戳的歌词行 |
| 元数据标签 | `[ar:]`、`[ti:]` 这类，不是歌词 |
| 行哈希 | 一行文本的 sha1 前 8 位，用来发现"这行被改过" |
| 快路径 | body 哈希一致时跳过逐行哈希比对 |
| 失效 | 标注对不上当前正文，该行不显示读音 |
