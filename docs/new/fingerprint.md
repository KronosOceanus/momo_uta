# 音频指纹与匹配规则

> 读者：要改曲库、歌单、歌词存储、人声缓存的人。
> 定位：讲清"一首音频怎么被认出是同一首"，以及这个身份被谁用、怎么用。
> 自成一体：不依赖其它文档；只引函数名，不写行号。

## 0. 三十秒版本

```text
一段音频 → 算出一个 12 位指纹 → 它就是这首歌的 uid
  曲库条目、歌单成员、歌词文件、人声缓存，全部按这个 uid 找

指纹和路径无关：
  移动、改名、换目录、换机器 → 指纹不变 → 歌词/人声/歌单还在
```

```text
真实例子：
  文件    /…/Love Forever.flac（12,780,338 字节，310.1 秒）
  指纹    ab6ffa725ba9
  歌词    data/lyrics/Love Forever - 清水翔太,加藤ミリヤ.ab6ffa725ba9.nhlrc
  人声    data/vocals/ab6ffa725ba9/vocals.wav
```

## 1. 为什么需要"身份"

### 1.1 路径哈希的问题

```text
旧做法：uid = md5(音频绝对路径)[:12]

后果：
  · 改名 / 移动目录 → uid 变 → 歌词、歌单、人声全部对不上
  · 换一台机器（路径不同）→ 全部对不上
  · 文件名不可读
  · 同一段音频放两个目录 → 两份身份、两份标注
```

### 1.2 歌名匹配的问题

```text
只用"歌名 - 歌手"当身份，会撞：
  · 同名不同歌（不同歌手、TV size / full / remix / off vocal）
  · 同名同歌手（同一首歌的多个版本）
  · 没有歌手的歌（只剩歌名）
  · 歌名会变（重新匹配歌词、改标签、改文件名）

真实曲库统计（1402 首）：
  不同标题 1363 个
  重名标题 37 组（涉及 76 首）
  同名 + 同歌手 13 组（涉及 26 首）
  没有歌手 211 首
```

### 1.3 目标

```text
身份必须跟着"内容"走，而不是"位置"或"名字"：
  · 移动/改名/换机器 → 不变
  · 同名不同歌 → 能区分
  · 同一段音频的拷贝 → 认为是同一首
  · 重新压制/转码 → 认为是另一段音频（合理）
```

## 2. 指纹定义

### 2.1 公式

```text
fingerprint(audio) = sha1(
    时长（0.1 秒精度）
  + 文件大小（字节）
  + 25% / 50% / 75% 处各 32KB 的原始字节
)[:12]
```

```text
伪代码：

  dur  = 解码时长，保留 1 位小数
  size = 文件字节数
  data = 三段采样拼起来
  fp   = sha1(f"{dur:.1f}|{size}|".encode() + data).hexdigest()[:12]
```

### 2.2 每个成分为什么选它

```text
时长
  · 来自解码器（mutagen；wav 用标准库兜底），不是文件头猜测
  · 和文件名、标签、路径无关
  · 0.1 秒精度：够区分不同版本，又不至于被毫秒级误差打乱

文件大小
  · 极便宜（stat 一次）
  · 增加第二重区分

三段 32KB 原始字节
  · 取文件的 25% / 50% / 75%，避开头部（ID3/FLAC 标签）和尾部（ID3v1/封面）
  · 三段而不是一段：避免中间恰好是静音导致不同歌相撞
  · 小文件（≤ 3×32KB）直接取前 96KB
```

### 2.3 实现细节

```text
采样位置：
  size <= 98304（3×32KB）→ 从 0 读到 98304（有多少读多少）
  否则对每个 pos ∈ {0.25, 0.5, 0.75}：
      off = int(size * pos) - 16384，夹到 [0, size - 32768]
      读 32768 字节

时长读取顺序：
  1) mutagen 能读 → info.length
  2) 读不了且是 .wav → 标准库 wave：帧数 / 采样率
  3) 都不行 → 用 "na" 参与哈希（仍然按内容算，不退回路径）
```

```text
读不了文件（不存在、权限、损坏）：
  退回 md5(路径)[:12]
  目的：永远有一个稳定 id，不抛错；测试占位文件也走这条
```

### 2.4 为什么不做全文件哈希

```text
全文件哈希最稳，但打开一首歌要读完整文件（几十 MB）。
1402 首的曲库，启动/扫库成本不可接受。
指纹只读约 96KB，毫秒级。
```

## 3. 索引缓存

### 3.1 位置与结构

```text
data/cache/fingerprints.json

{
  "_v": 2,                                  // 索引版本，读不懂就当空
  "/abs/path/song.flac": {
    "size": 12780338,
    "mtime": 1699999999.12,
    "fp": "ab6ffa725ba9"
  }
}
```

```text
key = 音频路径字符串（曲库扫描时的绝对路径）
失效条件：size 或 mtime 变了 → 重算
_v 不匹配 → 整个索引当空（算法升级时自动重建）
```

### 3.2 什么时候写盘

```text
fingerprint() 命中索引 → 直接返回
没命中 → 现算，更新内存，标记 dirty
scan_library() 结束时 flush() 一次写盘
```

```text
为什么不每算一次写一次：
  1402 首会变成 1402 次写盘；批量结束后写一次就够。
```

### 3.3 性能（实测，1402 首）

```text
首次扫库（索引为空）：约 2.5 秒
带索引再扫：        约 0.25 秒
索引文件本身：几十 KB 到几百 KB
```

```text
删掉索引不会丢数据，只是下次扫库重算一遍。
```

## 4. uid 被谁用

```text
曲库条目        CACHE[i]["uid"] = 指纹
歌单成员        playlists.json 里存 uid
歌词文件        data/lyrics/<歌名> - <歌手>.<指纹>.nhlrc
人声缓存        data/vocals/<指纹>/vocals.wav + meta.json
```

```text
不按指纹的东西（避免混淆）：
  · 歌单/标签/整体偏移/手改读音的旧数据里有"歌名 key"
    那是 md5(文件主干)[:12]，和指纹不是一回事
  · 波形缓存按音频路径
  · 播放器里的 idx 是"当前曲库里的位置"，不是身份
```

```text
idx 与 uid 的关系：
  idx 每次扫库都可能变；uid 跟内容走。
  接口里用 idx 定位当前会话的条目，再通过条目拿 uid 去查文件。
```

## 5. 匹配规则

### 5.1 打开一首歌 → 找歌词

```text
① 用条目 uid（指纹）查 data/lyrics：
     glob("*.​<指纹>.nhlrc")   ← 只认指纹后缀，不看前缀
     找不到再找 "*.​<指纹>.nhlrc.bak"
② 没有 → 看音频旁边的旧 .nhlrc：
     读到就复制进 data/lyrics（按指纹命名），然后删除旧文件
③ 没有 → 看音频旁边的 .lrc（只有正文）
④ 没有 → 歌词缓存（按歌名/歌手取）
```

```text
不再读取：
  data/lyrics 里文件名后缀是"旧路径哈希"的 nhlrc
  （不是当前音频的指纹 → 视为别人的文件）
```

### 5.2 保存

```text
写到 data/lyrics/<歌名> - <歌手>.<指纹>.nhlrc
文件名规则：
  · 前缀 "歌名 - 歌手"；没有歌手只写歌名；都空 → untitled
  · 非法字符 / \ : * ? " < > | 和控制字符 → _
  · 空白压成一个空格，去掉首尾空格/点
  · 前缀截断到 120 字节以内
  · 指纹永远保留在后缀

首次写入前备份成同名 .nhlrc.bak；之后再保存不覆盖 .bak。
```

```text
前缀只是给人看的：
  歌名/歌手变了，查找仍按指纹命中旧文件；
  保存时不会自动改前缀（文件名可能和当前标题不一致，这是可接受的）。
```

### 5.3 导入

```text
导入音频 + 同目录歌词（批量）：
  · 按文件名配对（去编号/后缀后比较），配不上 → 进"待匹配"
  · 读到 .nhlrc → 正文 + 读音一起导入
  · 身份不沿用：一律写成"当前音频指纹"的文件

导入单个歌词（LRC 工具栏）：
  · .lrc  → 只有正文
  · .nhlrc → 正文 + 读音
  · 同样写到当前音频的指纹文件（已有则备份后覆盖）
```

```text
所以"别人的歌词"导入后就是"当前音频的标注"，
文件里不记录来源指纹（不需要，也不参与查找）。
```

### 5.4 歌单成员

```text
新成员：加入时用当前条目的指纹 uid
旧成员：存的是路径哈希 uid
```

```text
旧成员的兼容（读时别名，不写盘、不迁移）：
  构建歌单时，对每个曲库条目额外算一次 md5(路径)[:12]
  成员 uid 在新 uid 里找不到 → 用旧 uid 别名找
  新旧 uid 指向同一首 → 只显示一次
找不到文件的成员 → 计入 missing，保留在文件里不删
```

```text
效果：
  旧歌单在曲库升级后仍能显示；
  新加的成员用指纹；
  文件本身不重写（没有隐式迁移）。
```

### 5.5 人声缓存

```text
位置：data/vocals/<指纹>/vocals.wav + meta.json
查找：直接用条目 uid（指纹）拼路径
指纹变了（重新压制/剪辑）→ 找不到旧缓存 → 重新分离
```

### 5.6 同一段音频的两份拷贝

```text
指纹相同 → 同一身份：
  · 共用一份歌词（data/lyrics 里一个文件）
  · 共用一份人声缓存
  · 歌单里只显示一次（uid 相同）
```

```text
真实曲库：1402 个条目、1350 个唯一指纹
  52 组重复指纹（涉及 104 个条目），例如：
    01 Piano Concerto Medley -dispel-.mp3
    Active Planets - Piano Concerto Medley -dispel-.mp3
  两段音频字节相同 → 同一份标注
```

### 5.7 文件不存在

```text
曲库：扫不到的文件不进 CACHE
歌单：成员保留，missing 计数 +1
歌词文件：留在 data/lyrics（孤儿），不自动删除
人声缓存：留在 data/vocals，不自动删除
```

## 6. 旧数据兼容

```text
音频旁边的旧 .nhlrc
  → 读取时复制进 data/lyrics（按指纹命名）
  → 复制成功后删除旧文件（避免两份真相）

data/lyrics 里的旧"路径哈希"文件
  → 不再读取；不迁移、不兜底
  → 它们会留在目录里成为孤儿，需要手动清理

旧歌单成员（路径哈希）
  → 读时别名映射（见 §5.4），不写盘

旧 readings.json（手改读音）
  → 写 nhlrc 时并入 seg，然后清空该歌的条目
  → 之后不再重放
```

## 7. 边界与已知限制

```text
① 重新压制 / 转码 / 剪辑
   字节和时长都变 → 指纹变 → 视为另一段音频（重新注音、重新分离）

② 重新打标签（改 ID3 / 加封面）
   文件大小变、采样位置随之后移 → 指纹可能变
   这是当前采样策略的已知代价；
   若要更稳，需要按"解码后的音频"取样（读盘/解码更重）

③ 指纹碰撞
   12 位十六进制（48 bit）；
   曲库规模下实际碰撞概率可忽略；
   真出现时表现为"两首歌共用一份标注"

④ 路径哈希回退
   只发生在文件读不了时；
   这类身份仍然"绑路径"，移动后会变

⑤ 同一段音频的两份拷贝
   共用标注是设计选择，不是错误；
   如果你希望"两份各自独立"，需要把路径重新纳入身份（不推荐）

⑥ 改名/换目录后
   歌词/人声跟着走；
   歌单里的旧成员靠别名仍能显示；
   但如果你删除了原文件，别名也就失效了
```

## 8. 运维

```text
备份：
  data/lyrics/   用户资产，建议备份/进 git
  data/vocals/   可重算（但很贵），按需备份；不进 git
  data/cache/fingerprints.json  可删，会自动重建

换机器：
  1) 复制 data/lyrics（可选 data/vocals）
  2) 首次扫库会自动重算指纹索引
  3) 音乐路径可以不同，指纹不受影响

清理：
  make clean-cache    删 data/cache/{lyrics,wave}
  make clean-vocals   删 data/vocals
  rm data/cache/fingerprints.json  只影响下次扫库速度

排查：
  · 歌词找不到 → 看 data/lyrics 里有没有 *.<指纹>.nhlrc
  · 指纹和预期不符 → 看文件是否被重新压制/改标签
  · 歌单空了 → 检查成员 uid 与当前条目 uid 是否能按别名对上
```

## 10. 术语

| 词 | 意思 |
|---|---|
| 指纹 | 12 位十六进制，由时长 + 大小 + 三段采样算出 |
| uid | 当前实现里就是指纹；曲库/歌单/歌词/人声统一用它 |
| 索引 | `data/cache/fingerprints.json`，路径 → (size, mtime, 指纹) |
| 旧 uid / legacy uid | 旧版按路径 md5 算出的 id；歌单兼容时用作别名 |
| 别名 | 读歌单时把旧 uid 映射到当前条目的机制，不写盘 |
| 孤儿 | 音频已删除/移动后，留在 data/lyrics 或 data/vocals 里的文件 |
| 路径回退 | 文件读不了时退回 `md5(路径)`，保证有稳定 id |
