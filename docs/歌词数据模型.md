# 歌词数据模型设计

> 状态：设计提案，尚未实现。
> 目标：消除 `body_rows` / `compact lines` 两套行空间，避免空行、插入、删除、重排导致的索引错位。

## 0. 一句话

```text
只有一份 rows
每行有稳定身份
播放、编辑、保存、翻译、metadata 都引用同一份 rows
```

```text
compact 不再是第二份权威数据
它只是从 rows 派生出来的播放视图。
```

## 1. 当前问题

现在同时存在：

```text
body_rows
  编辑器/文件顺序
  包含空行、metadata 行、草稿行

compact lines
  播放/注音/翻译顺序
  不包含空行和 metadata
```

由此产生：

```text
annotation i      相对 compact
trans i           相对 compact
lid/tid           相对 compact
metadata.before   相对 compact
编辑器 EROWS      相对 body
```

任何跨边界代码都必须做：

```text
body index → compact index
compact index → body index
```

漏一次就会出现：

```text
读音错行
翻译错行
metadata 插错位置
lid/tid 丢失
空行导致整体偏移
```

这不是单点 bug，是模型问题。

## 2. 设计原则

```text
1. 行只存在一份
2. 行身份不依赖位置
3. 空行只是行，不是索引偏移
4. 播放行是派生结果，不是第二份数据
5. 任何持久化数据按身份关联，不按第几行关联
```

## 3. 核心模型

### 3.1 Row

```ts
type Row = {
  id: string;              // 编辑器行身份
  kind: "lyric" | "blank" | "metadata";
  text: string;            // lyric 正文 / metadata 原始行 / blank ""
  t: number | null;        // lyric 时间戳
  lid: string | null;      // lyric 行身份
  tokens: Token[];         // lyric 的 token
  trans: string;           // lyric 译文
}
```

```ts
type Token = {
  tid: string;
  start: number;
  end: number;
  base: string;
  ruby: string | null;
  level: string | null;
}
```

规则：

```text
kind=lyric
  → 有 lid/t/tokens/trans
  → 参与播放、注音、翻译

kind=blank
  → text=""
  → 不参与播放/注音/翻译
  → 仍是 rows 中的一行

kind=metadata
  → text 是原始 [ar:] / [ti:] / [offset:] 行
  → 不参与播放/注音/翻译
  → 仍是 rows 中的一行
```

### 3.2 播放视图

```ts
playable = rows.filter(r =>
  r.kind === "lyric" && r.t !== null
);
```

播放器只拿 `playable`。

```text
playable index 只用于显示/播放导航
不是身份
```

### 3.3 为什么 metadata 也是 row

现在 metadata 用：

```text
before: compact 行号
```

空行一插就错位。

改成：

```text
metadata 自己就是 rows 中的一行
```

保存时按 rows 顺序直接输出，不需要 before 映射。

## 4. nhlrc 存储

正文仍然按 rows 顺序写：

```lrc
[ar:歌手]
[00:01.00]君

[00:03.00]花
```

尾部只存 lyric 行的扩展信息：

```json
{
  "v": 1,
  "lines": [
    {
      "i": 0,
      "lid": "l_aaa",
      "h": "1234abcd",
      "seg": [["君", "きみ", "A"]],
      "tid": ["t_aaa"]
    },
    {
      "i": 1,
      "lid": "l_bbb",
      "h": "abcd1234",
      "seg": [["花", "はな", "A"]],
      "tid": ["t_bbb"]
    }
  ],
  "trans_lang": "zh",
  "trans": [
    {"i": 0, "lid": "l_aaa", "h": "1234abcd", "text": "你"},
    {"i": 1, "lid": "l_bbb", "h": "abcd1234", "text": "花"}
  ]
}
```

说明：

```text
i   保留给旧读取器和调试
lid 是新代码的真正身份
h   只做文本校验
```

新代码：

```text
读 lines/trans 时优先按 lid
缺失 lid 才按 i + h 兼容
写时同时写 i + lid
```

这样旧版本仍能读新文件，新版本能精确处理行移动。

## 5. 加载

### 5.1 旧文件没有 lid

```text
解析正文，得到 rows 和 compact
按 compact 顺序生成 legacy lid
旧 trans 的 i 映射到 legacy lid
旧 annotation 的 i 映射到 legacy lid
```

```text
只在内存中生成
不立即重写文件
```

### 5.2 新文件有 lid

```text
正文 → rows
lines / trans 按 lid 挂回对应 lyric row
```

```text
lid 找不到 → 丢弃该条
lid 重复 → 后出现的降级为 legacy/跳过
```

### 5.3 返回给前端

```json
{
  "rows": [
    {"id":"r1","kind":"metadata","text":"[ar:歌手]","t":null,"lid":null},
    {"id":"r2","kind":"lyric","text":"君","t":1.0,"lid":"l_aaa","tokens":[...],"trans":"你"},
    {"id":"r3","kind":"blank","text":"","t":null,"lid":null},
    {"id":"r4","kind":"lyric","text":"花","t":3.0,"lid":"l_bbb","tokens":[...],"trans":"花"}
  ]
}
```

不再返回两套：

```text
body_rows
lines
line_ids
token_ids
```

前端只消费 `rows`。

## 6. 保存

```text
POST /api/lrc save
{
  "rows": [...],
  "version": "..."
}
```

后端：

```text
1. 校验 rows 顺序、row id、lid
2. lyric rows 按 lid 找旧 row
3. 未改 token 保留 tid/ruby/level
4. 新 token 重新注音并分配 tid
5. metadata/blank 原样写正文
6. lines/trans 按 lid 写尾部
```

不再需要：

```text
body_to_lyric
annotation_index
_map_new_to_old
metadata.before 映射
```

## 7. 编辑器

`EROWS` 就是 rows。

```text
输入正文
  → 更新 lyric row
  → 重新计算 token span

加空行
  → rows.splice(pos, 0, blank row)
  → 不影响任何 lid

删除行
  → rows.splice
  → 其他行不变

拆行
  → 原 row 保留 id/lid
  → 新 row 新 id
  → 完整 token 迁移

合并行
  → 保留内容主体 row 的 id/lid
  → 另一行 token 合并

metadata
  → kind=metadata
  → 原样显示/保存
```

`lrcText()`：

```text
rows.map(row => serialized line)
```

不再单独维护：

```text
LRC_METADATA
body_rows
```

## 8. 行操作规则

| 操作 | row id | lid | tokens | trans |
|---|---|---|---|---|
| 插入空行 | 新 | 无 | 无 | 无 |
| 删除空行 | 删除 | 无 | 无 | 无 |
| 插入歌词 | 新 | 新 | 新 | 空 |
| 删除歌词 | 删除 | 删除 | 删除 | 删除 |
| 上下移动 | 不变 | 不变 | 不变 | 不变 |
| 改时间 | 不变 | 不变 | 不变 | 不变 |
| 改正文 | 不变 | 不变 | 未改 token 保留 | 保留 |
| 改翻译 | 不变 | 不变 | 不变 | 更新 |
| 拆行 | 原侧保留 | 内容主体保留 | 完整 token 迁移 | 跟随内容 |
| 合并 | 目标保留 | 内容主体保留 | 完整 token 合并 | 跟随内容 |

## 9. 身份规则

```text
row.id
  只在当前编辑器文档内唯一
  用于 UI、undo/redo、metadata/blank 行定位

lid
  lyric 行身份
  跨插入/删除/移动保持

tid
  token 身份
  跨行移动保持
```

```text
idx
  永远只做展示
  不进入任何持久化身份
```

## 10. 旧数据兼容

不设计迁移脚本。

```text
旧 nhlrc
  → 读取时生成 legacy lid
  → 内存统一成 rows
  → 用户保存后写入 lid
```

```text
旧前端/旧读取器
  → 仍能按 i 读 lines/trans
  → 新文件继续写 i
```

```text
不升级 v
不要求一次性改所有旧文件
```

## 11. 实施阶段

### 第 1 步：核心 rows

```text
lrc_doc 增加 rows 解析/序列化
lyric/blank/metadata 三种 kind
playable 派生
```

### 第 2 步：存储 lid

```text
lines/trans 增加 lid
读取优先 lid
写入 lid + i
```

### 第 3 步：service

```text
save_lyrics 改为 rows 输入
删除 body_to_lyric / annotation_index
按 lid 合并 annotation/token
```

### 第 4 步：API

```text
/api/lrc load / save 使用 rows
```

### 第 5 步：编辑器

```text
EROWS 改为 rows
metadata/blank 统一
删除 LRC_METADATA 独立状态
```

### 第 6 步：播放

```text
song_payload 从 rows 派生 playable
不再维护 compact lines 作为权威
```

### 第 7 步：清理

```text
删除 _map_new_to_old
删除 _body_layout
删除 metadata.before 映射
删除 body/compact 双索引测试
```

## 12. 验收

```text
空行在任意位置
插入/删除空行
插入/删除歌词行
上下移动
重复歌词交换
拆行/合并
改正文
改读音
改翻译
导出/重新导入
旧 nhlrc 无 lid
新 nhlrc 有 lid
```

全部满足：

```text
lid/tid/trans/metadata 都跟内容走
不因空行改变
```

## 13. 风险

```text
这是结构性重构，不是小修
会同时改 core/service/API/前端/测试
metadata 的 UI 呈现需要决定
旧读取器兼容需要保留 i
```

但继续维护两套行空间，风险更大：

```text
每加一个功能都要再写一次 index 映射
每漏一次就是一类错行 bug
```

## 14. 结论

```text
采用：单一 rows + 稳定 lid/tid + 派生播放视图
停止：body_rows / compact 双权威 + 到处 annotation_index
```

这是比继续打补丁更小的长期成本。
