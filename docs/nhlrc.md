# nhlrc：带振假名的歌词文件

> 读者：要改歌词读写、导入导出、标注落盘的人。
> 定位：格式规范 + 读写规则。自成一体：先讲 LRC 是什么，再讲我们多加了什么。

## 0. 三十秒版本

```text
.nhlrc = 一份普通 LRC 歌词 + 文件末尾一段 JSON（振假名标注）

普通 LRC 播放器读前半段，行为不变；
我们的程序读到 "#NHLRC 1" 之后，把每个汉字该读什么也读出来。
```

```text
[ti:君の名前]
[00:12.34]君の名前を呼んで
[00:16.02]ずっと覚えている

#NHLRC 1
{
 "v": 1,
 "gen": "nihonco 0.1",
 "body": "03f12d07",
 "lines": [
  {"i": 0, "h": "d6bdabed", "seg": [["君","きみ","AB"],["の",null,null],["名前","なまえ","A"],["を呼んで",null,null]]},
  {"i": 1, "h": "0201bf8f", "seg": [["ずっと",null,null],["覚","おぼ","A"],["えている",null,null]]}
 ]
}
```

```text
存在位置：
  data/lyrics/<歌名> - <歌手>.<音频指纹>.nhlrc
  首次写入时备份成 data/lyrics/bak/ 下的同名 .nhlrc.bak
```

## 1. 它解决什么问题

```text
LRC 只有两样东西：
  [mm:ss.xx]文本        时间 + 文本
  [ar:][ti:] 等          元数据标签
没有"哪个汉字读什么"的位置。
```

```text
三种"不改格式"的存法都不行：
  ① 读音写进正文：  君(きみ)の名前
     正文不再是正常歌词，其它播放器会显示括号注音，打轴也容易错位
  ② 自定义符号：    君{きみ}の
     被当普通字符，搜索/排序全乱
  ③ 纯 JSON：       {"lrc": "...", "ruby": [...]}
     人不可读、diff 难看、普通播放器打不开
```

```text
采用的设计：
  正文保持 100% 合法 LRC（兼容、可退化），
  读音放在文件末尾一段 JSON 里（可读、可扩展、普通播放器会当无时间戳行忽略）。
```

## 2. 身份与存储

### 2.1 身份：音频指纹

```text
每首歌的身份 = 音频指纹，和路径、文件名无关：

  sha1(
      时长（0.1 秒精度）
    + 文件大小
    + 文件 25% / 50% / 75% 处各 32KB 的哈希
  )[:12]

例：12,780,338 字节、310.1 秒 → ab6ffa725ba9
```

```text
为什么不是路径：
  移动 / 改名 / 换目录 / 换机器 → 指纹不变 → 标注还在
  同一段音频的两份拷贝 → 指纹相同 → 共用同一份标注

什么时候会变：
  重新压制 / 剪辑 / 转码 → 新身份（视为另一段音频）
  重新打标签 / 加封面 → 文件大小和采样位置可能变，指纹可能变
```

### 2.2 位置与命名

```text
目录：data/lyrics/
文件：<歌名> - <歌手>.<指纹>.nhlrc
备份：data/lyrics/bak/<歌名> - <歌手>.<指纹>.nhlrc.bak
```

```text
命名规则：
  · 有歌手："歌名 - 歌手.<指纹>.nhlrc"
  · 没歌手："歌名.<指纹>.nhlrc"
  · 都没有："untitled.<指纹>.nhlrc"
  · 非法字符 / \ : * ? " < > | 和控制字符 → 替换成 _
  · 连续空白压成一个空格；去掉首尾空格和点
  · 前缀按 UTF-8 截断到 120 字节以内
  · 指纹永远保留在后缀
```

```text
查找只认后缀：
  data/lyrics/*.<指纹>.nhlrc
  data/lyrics/bak/*.<指纹>.nhlrc.bak

前缀是给人看的：
  歌名/歌手变了，仍按指纹命中同一份文件；
  保存不会自动改前缀（文件名可能和当前标题不一致）。
```

## 3. 文件结构

```text
<LRC 正文>
<空行>
#NHLRC 1
<JSON 尾部>
```

```text
硬规则：
  · 标记行之前的所有内容，必须是一份完整的、合法的 LRC
  · 标记行形如 "#NHLRC <版本号>"；写入方固定写 "#NHLRC 1"
    读取方只要求行首（去空白后）以 "#NHLRC" 开头
  · 标记之后是 JSON 对象；解析失败 → 整个尾部作废（当纯 LRC 处理）
  · 编码 UTF-8，换行 \n；读取时容忍首行 BOM
  · 没有任何标注时，文件就是纯 LRC（不写标记、不写尾部）
```

### 3.1 正文解析器接受的写法

```text
[mm:ss.xx]文本             标准
[mm:ss]文本                无小数
[mm:ss.xx-1]文本           KTV 变体（尾部 -1 忽略）
{"t":毫秒,"c":[{"tx":"…"}]}   网易云逐行 JSON（逐行解析，不是整文件 JSON）
[ar:][ti:][al:][by:][offset:][length:][re:][ve:][la:][id:][tool:]
                           元数据标签：不进歌词行，单独保留
其余非空行                   "未打点草稿行"，原样保留
```

```text
不支持的写法（会被当成草稿文本，不会被理解）：
  · 增强型 LRC：<00:12.34>逐字标签
  · 一行多个时间戳：[00:12.34][00:15.67]同一句
```

## 4. 尾部字段

```json
{
 "v": 1,
 "gen": "nihonco 0.1",
 "body": "03f12d07",
 "lines": [
  {"i": 0, "h": "d6bdabed", "seg": [["君","きみ","AB"],["の",null,null]]}
 ]
}
```

```text
字段    类型     必填   含义
v       int      是     格式版本，当前 1；只增不改
gen     string   否     生成器标识（排查问题用，不参与校验）
body    string   否     整篇正文哈希（sha1 前 8 位）：校验快路径，见 §5.2
lines   array    是     每行一条标注，按 i 升序
  i     int      是     正文行序号（从 0 开始）
  h     string   是     该行文本哈希（sha1 前 8 位）
  seg   array    是     片段数组，见 §4.1
```

### 4.1 `seg` 片段

```text
seg = [[base, ruby, level], ...]        // 每个元素是三元组

base   该片段的原文（必须拼起来等于整行文本）
ruby   平假名读音；null = 这段不注音（假名、标点、送り仮名）
level  A / AB / B / C / null
```

```text
例：君の名前を呼んで
  [["君","きみ","AB"], ["の",null,null], ["名前","なまえ","A"], ["を呼んで",null,null]]

规范：
  · base 拼接必须严格等于正文行文本（含标点、空格）
  · ruby 只能是平假名（可以带 ー）
  · level=K 等价于 ruby=null；无读音片段写 null
```

### 4.2 "一行"怎么数

```text
i 数的是正文解析后的行序号：
  · 跳过空行
  · 跳过元数据标签（[ar:] 这类，它们不进 lines）
  · 保留未打点的草稿行（t=null 也是行）
  · 保留带时间戳的普通行（包括"作词 : X"这种信息行）
```

## 5. 校验与对齐

### 5.1 三道检查

读取时 `lrc_doc.annotations_for(lines, tail, strict)` 对每条标注检查：

```text
① 下标：0 <= i < len(lines)，否则丢弃
② 拼接：seg 里 base 拼起来必须等于该行文本，否则丢弃
③ 哈希：strict 时 h 必须等于该行文本哈希，否则丢弃
```

### 5.2 `body` 哈希：快路径

```text
body = sha1(整篇正文)[:8]

读取时：
  body 与当前正文哈希一致
      → 正文没动过 → 跳过 ③（不再逐行比 h），仍然做 ① ②
  body 缺失 / 不一致
      → 逐行比 h
```

```text
为什么两套都要：
  · 逐行哈希能定位"哪一行被改了"
  · body 哈希能一次判断"整篇没动"，省掉逐行比较
  · 即使 body 一致，仍校验拼接：尾部被改坏时不会错位
```

### 5.3 按内容对齐

```text
编辑正文后（插入/删除/移动行），读取与保存都会先对齐：

第一轮：位置 + 内容都一致 → 直接认领
        （没动过的文件，这一步就是唯一答案，也最快）
第二轮：剩下的标注按"文本完全相同"配对，先进先出
第三轮：没人认领的行 → 没有标注（重新注音）
```

```text
效果：
  插入一行     → 其余行按内容找回，新行重新注音
  删除一行     → 其余行找回
  移动两行     → 读音跟着内容走
  只改时间戳   → 文本没变，读音保留
  改了一个字   → 只有那一行对不上（重新注音）
```

```text
重复行（副歌同一句出现两次、两处读音不同）：
  按出现顺序配对；交换这两个相同行的顺序时可能配错。
  要彻底解决需要给每行加稳定 id（尚未实现）。
```

### 5.4 失效场景

| 场景 | 结果 | 恢复方式 |
|---|---|---|
| 改了一行的文字 | 该行 h 对不上 → 只这一行标注作废 | 保存时重新注音 |
| 插入/删除/移动行 | 按内容对齐，没改字的行保留 | 新行重新注音 |
| 两行完全相同的文本交换顺序 | 按顺序配对，可能配错 | 手动改一次读音 |
| 尾部 JSON 坏了 | 尾部整体作废 → 当纯 LRC 读 | 重新注音 / 保存 |

```text
作废的行不会"错位显示"：那一行按普通歌词显示，没有 ruby。
```

## 6. 读写规则

### 6.1 加载

```text
文件优先级：
  1) data/lyrics/<歌名> - <歌手>.<指纹>.nhlrc（只认指纹后缀）
  2) 歌词缓存（抓取结果，可能带 nhlrc_annotations）
  3) 都没有 → 没有歌词（触发懒匹配）
```

```text
特殊情况：
  · .nhlrc 正文为空（0 行文本）→ 视为没有歌词
  · 尾部 JSON 解析失败 → 当纯 LRC 读
```

```text
标注来源：
  · .nhlrc → 按 §5 校验 + 对齐
  · 歌词缓存 → nhlrc_annotations 字段（同样的三元组结构）
  · 都没有 → 打开后自动注音，再落盘
```

### 6.2 保存

```text
输入：编辑器里的行（t + 文本）
步骤：
  ① 读当前文件，拿 metadata（[ti:] 这类标签）与已有标注
  ② 按内容对齐已有标注到新行序（§5.3）
  ③ 逐行决定标注：
       对齐到的行 → 沿用已有标注
       没对齐到 / 改了字的行 → 重新注音
  ④ 生成正文：行 + 元数据按原位置插回
  ⑤ 生成尾部：render_nhlrc(行, 元数据, 标注)
  ⑥ 写 data/lyrics/<歌名> - <歌手>.<指纹>.nhlrc（覆盖）
```

```text
保护：
  · 没有非空歌词行 → 拒绝保存（不写空文件）
  · 首次写之前，把现有的 nhlrc 备份成 data/lyrics/bak/ 下的同名 .nhlrc.bak
    （之后再保存不会覆盖 .bak）
  · "恢复最初"用 data/lyrics/bak/ 下的 .nhlrc.bak
  · disabled 文档不会成为可恢复歌词备份
```

### 6.3 自动注音

```text
打开歌曲时只在内存生成 ruby/rm/ky；
不写 data/lyrics，也不把缓存歌词提升成 nhlrc。

只有用户保存、导入、pick、恢复备份才会写权威文件。
```

### 6.4 缓存里的标注

```text
歌词缓存 JSON 里可能带：
  "nhlrc_annotations": {"0": [["君","きみ","A"], …], "1": …}

结构 = 尾部 lines 的 i → seg（不带 h；读取时按拼接校验）
用途 = 网络缓存的可选读音副本；永远不能覆盖 nhlrc，
       也不会因为打开歌曲被提升成 nhlrc。
```

### 6.5 手改读音

```text
用户在界面上点候选或手输读音
  → /api/line
  → 后端：读文件 → 对齐 → 重算这一行（带这次 override）
  → 立即写回 data/lyrics/<歌名> - <歌手>.<指纹>.nhlrc（正文不变，尾部更新）
  → 返回新的 ruby / 罗马音 / 键位
```

```text
所以：
  · 手改读音就是该行 seg 的一部分，nhlrc 是唯一真相
  · 打开时直接读文件，没有额外的"重放"步骤
```

## 7. 导入 / 导出

### 7.1 导入音频（歌单右键「导入音乐」）

```text
规则：
  · 按文件名配对同目录的歌词（.nhlrc 优先于 .lrc）
  · 读到 .nhlrc → 正文 + 读音直接写权威 data/lyrics
  · 只有音频没有歌词 → 进歌单，标记"待匹配"
  · 歌词少于 3 行 → 视为没有可用歌词
```

```text
导入只读源文件，不改源文件、不往源目录写东西。
导入完成后缓存清空也不会丢用户歌词。
```

### 7.2 导入歌词（LRC 工具栏「导入」）

```text
接受 .lrc / .nhlrc：
  · .lrc  → 正文（没有读音可带）
  · .nhlrc → 正文 + 读音
  · 一律写当前音频的指纹文件（已有则备份后覆盖）
  · 文件空 → 报错
```

```text
导入后这份歌词就属于当前音频；
不记录来源身份（来源不参与查找）。
```

### 7.3 导出（LRC 工具栏「导出」）

```text
默认文件名：<歌名>.nhlrc
扩展名改成 .lrc → 只写正文（纯 LRC，不含尾部）
否则            → 写完整 .nhlrc（正文 + 尾部）

导出的尾部按当前内容重新生成：
  · 未知的尾部字段会丢（只保留 v/gen/body/lines）
  · 需要保留的信息请放在正文元数据标签里
```

## 8. 与普通 LRC 的兼容性

```text
能保证的：
  · 标记行之前对任何 LRC 播放器都是合法文件
  · 把 .nhlrc 改名成 .lrc 也能播（尾部是无时间戳行）
  · 没有标注时，文件本来就是纯 LRC
```

```text
不能保证的：
  · 尾部是无时间戳的非空行：多数播放器忽略，少数会显示 JSON 文本
  · 草稿行（没有时间戳的歌词）各播放器行为不同
  · 增强型逐字时间、多时间戳不支持（见 §3.1）
```

```text
只想要"绝对兼容"：用「导出」存成 .lrc（只有正文）。
```

## 9. 版本与演进

```text
· 正文永远不为新功能变脏（不能把标注塞进正文）
· 尾部是唯一扩展点；读取方必须忽略不认识的字段
· v 只增不改；遇到更高 v 时：
    a) 按已知字段尽力读（推荐）
    b) 整份当纯 LRC 读（保守）
· 保存时尾部按当前内容重新生成，未知字段会丢（§7.3）
```

## 10. 完整示例与流程

### 10.1 一个真实文件

```text
[ti:君の名前]
[ar:テスト]
[00:12.34]君の名前を呼んで
[00:16.02]ずっと覚えている
[00:20.10]また会おう

#NHLRC 1
{
 "v": 1,
 "gen": "nihonco 0.1",
 "body": "03f12d07",
 "lines": [
  {"i": 0, "h": "d6bdabed", "seg": [["君","きみ","AB"],["の",null,null],["名前","なまえ","A"],["を呼んで",null,null]]},
  {"i": 1, "h": "0201bf8f", "seg": [["ずっと",null,null],["覚","おぼ","A"],["えている",null,null]]},
  {"i": 2, "h": "0c3d2074", "seg": [["また",null,null],["会","あ","A"],["おう",null,null]]}
 ]
}
```

```text
核对：
  body   = sha1(正文)[:8]              = 03f12d07
  i=0 h  = sha1("君の名前を呼んで")[:8] = d6bdabed
  i=1 h  = sha1("ずっと覚えている")[:8] = 0201bf8f
  i=2 h  = sha1("また会おう")[:8]       = 0c3d2074
```

### 10.2 写流程

```text
编辑器行（t + 文本）
   │
   ├─ render(lines, metadata) ────────────────► 正文
   │
   ├─ 对齐已有标注（§5.3）→ 沿用/重新注音
   │
   └─ render_nhlrc(lines, metadata, 标注) ────► 正文 + 尾部
                                                │
                        首次写：备份到 data/lyrics/bak/
                                                │
                                     写 data/lyrics/<…>.<指纹>.nhlrc
```

### 10.3 读流程

```text
读文件
  │
  ├─ 找 "#NHLRC" 标记 → 拆成（正文, 尾部 JSON）
  │
  ├─ 解析正文 → lines + metadata
  │
  ├─ 校验尾部：body 快路径 + 下标 + 拼接（+ 必要时逐行 h）
  │
  └─ 交给上层：lines（带 ruby）+ annotations（按 i 对齐）
```

## 11. 已知限制

```text
① 行级哈希，不是字符级
   一行改一个字，整行标注作废（避免错位）

② 下标映射依赖正文行顺序
   外部工具重排/删除行 → 靠内容对齐找回；完全相同文本的行可能配错

③ 尾部会被重写
   保存时按当前内容重新生成，未知字段丢失

④ 不做压缩/加密
   一首 40 行的歌，尾部大小与正文同量级

⑤ 只支持 UTF-8
   读取容忍首行 BOM；写入不带 BOM

⑥ 正文解析能力有限
   增强型逐字时间、一行多时间戳不支持

⑦ 空文件保护
   没有非空歌词行时：不自动写、保存被拒；显式删除写 disabled 文档
```

## 13. 术语表

| 词 | 意思 |
|---|---|
| LRC | 最常见的歌词文本格式：`[mm:ss.xx]文本` |
| 正文（body） | 标记行之前的 LRC 部分 |
| 尾部（tail） | `#NHLRC` 之后的 JSON |
| 振假名（ruby） | 标在汉字上的读音 |
| 片段（segment） | 连续原文 + 可选读音的最小单位 |
| 草稿行 | 还没打时间戳的歌词行 |
| 元数据标签 | `[ar:]`、`[ti:]` 这类，不是歌词 |
| 行哈希 | 一行文本的 sha1 前 8 位，用来发现"这行被改过" |
| 快路径 | body 哈希一致时跳过逐行哈希比对 |
| 失效 | 标注对不上当前正文，该行不显示读音 |
| 指纹 | 音频身份（时长 + 大小 + 三段采样），和路径无关 |
