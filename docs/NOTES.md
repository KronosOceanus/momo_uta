## 总原则（优先于一切局部优化）

```text
1. 正确性优先于精度
   先把"标对"做对，再谈"多标"。宁可少标，不可标错。

2. 泛化优先于跑分
   评测集涨 0.5pp 但只在那 30 首歌上成立，不算进步。
   任何改动要在留出集（lyrics_test）上同样成立，才算数。

3. 不确定规则不默认开
   判据依赖"我们手头的表/抽样/手选名单"的规则（R1/R3/R4），
   其精度与泛化能力都无法事先保证 → 默认关闭，可整套接入但需自担风险。

4. 一条规则必须能一句话说清
   "什么时候成立、为什么"。说不清的规则迟早以难查的方式出错，
   且会把"运气"伪装成"知识"（例：固有名詞收紧，已回滚）。
```

**为什么强调泛化**：评测集只有 30 首开发 + 20 首留出，样本小到
0.5pp 的变化可能只是噪声；而用户输入是任意的。在小样本上过拟合，
等于把"评测集特化"当成"能力"。

## 送り仮名对齐：93 → 7（2026-11）

一开始还剩 93 处「对齐失败」，抽出来看，其实是三类问题：

```text
① 送り仮名首字与词干末音相同（最多）
     歌う うたう / 疑う うたがう / 痛い いたい / 笑わ / 立た / 急い / 祝い / 微か
     原因：定位假名块时 find("う", 0) 命中了读音开头的「う」，汉字块分到 0 个音节
     修法：假名块必须从「汉字块至少吃掉一个音节」之后开始找

② 表记读音对不上活用形
     突っ込む(つっこむ) / 思える(おもえる) / 読める / 飲める / 払える / 引込める
     原因：[6]語彙素読み 给的是词干形（ツキコム），和 surface 对不上
     修法：对齐失败时退回 [9]発音形出現形 再试一次

③ 结构性例外（不修）
     一、二 / 四、五    带标点的数字
     満タン            片假名混入
     云フ              历史假名遣
```

结果：93 → **7**，且 7 处全是 ③ 这类结构问题。
coverage 75.3% → 76.1%，precision 不变（91.1%）。

### 回归检查（改动前 vs 改动后，逐 span 对比）

保留旧版副本，跑同一份 gold，逐 span 比对结论：

```text
变好 39 处 / 变差 0 处
新增标注 71 处，其中读音含长音符「ー」的 0 处
人工抽 10 个新增标注，全部正确（疑→うたが、買→か、会→あ、示→しめ…）
```

影响面小是结构决定的：这两处改动只在「对齐失败」这条分支上生效，
正常情况下根本走不到，所以不会波及已有的正确结果。

**这个做法以后沿用**：改判定逻辑时留一份旧副本，跑同一份 gold 做逐 span diff，
看到"变差 0"才收。

## 首选读音的取法（2026-11）

弃权原因里最大的一类是「非首选读音」，而"首选"本身怎么定，影响很大。

```text
最初   JMdict 条目顺序的第一个常用读音
       街→がい、降る→くだる、様→さま   ← 与语料里的常用读法不符
后来   分词器对裸词给出的读音（在常用集合内时优先）
       街→まち、降る→ふる、様→よう
补充   data/curated/primary_override.json 人工纠偏（私→わたし、僕→ぼく…）
```

代价与收益（相对 JMdict 顺序版）：

```text
lyrics   96.3%/80.6% → 95.8%/82.0%      precision −0.5pp，coverage +1.4pp
prose    75.5%/62.6% → 73.9%/64.1%
整体     91.1%/76.1% → 90.3%/77.6%      precision −0.8pp，coverage +1.5pp
```

选择留后者：**用户看到"街/様/降る"有假名比看到一堆弃权点更重要**，
而 precision 只降了不到 1 个点。若以后要严格精度优先，把这一段改回去即可。

### 弃权是否值得（关键实验）

把弃权的地方强行用「UniDic 读音」标上，和 gold 比：

| 原因 | 标了会对 | 标了会错 | 准确率 |
|---|---|---|---|
| 非首选读音 | 269 | 184 | 59% |
| 数詞 | 24 | 7 | 77% |
| 熟字訓冲突 | 16 | 9 | 64% |
| OOV | 34 | 62 | 35% |
| 固有名詞 | 9 | 25 | 26% |
| **合计** | **352** | **287** | **55%** |

结论：**弃权是对的**。硬标上去只有 55% 正确率，等于把精度从 91% 拉到 78%。
唯一值得再挖的是「非首选读音」这一档（59%），但它也是硬币正反面级别。

## M3：LLM 消歧（2026-11）

架构（抄 JRM 的纪律）：**候选约束 + 只填空缺**。

```text
候选   候选集合 = 常用读音 ∪ 熟字訓读音；长度 <2 的不问
调用   离线批量预取（10 条/请求），结果落 data/cache/llm/choices.json
应用   只覆盖「原本弃权(C)」的 segment，不覆盖已确定的判定
校验   返回的读音必须在候选里，否则当没问
```

结果（flash 模型，全量 5809 个多候选词）：

| 版本 | precision | coverage | 判对 | 判错 |
|---|---|---|---|---|
| 不开 LLM | **90.7%** | 73.0% | 3428 | 352 |
| LLM conf≥0.95（全部读音候选） | 90.2% | 77.6% | 3605 | 391 |
| LLM conf≥0.95（常用读音候选） | 90.5% | 74.1% | 3481 | 366 |

### 踩到的坑

```text
1. 候选里混进生僻读音（何時 的候选里出现过 なん）→ 模型挑错
   修法：候选只给 common 读音（common_readings.json）
2. pro 是 reasoning 模型：一次请求 ~1000 token 花在思考上，
   max_tokens 不够时 content 直接为空 → 全量要 5 小时，放弃
3. 一开始让 LLM 覆盖所有多候选词，precision 掉到 85.7%
   修法：只填原本弃权的 C
```

### 结论

```text
LLM 层净收益很小：coverage +1~4pp，precision −0.2~0.5pp
补充准确率 ~84%（标对 215 个的代价是多错 42 个）
→ 默认关闭，make eval-llm 可开
```

为什么 LLM 会判错（三类）：

```text
A 候选噪声   给了生僻读音，它挑了个"看起来像"的
B 真歧义     我(わ/わが/われ)、幸(さち/さいわい/しあわせ) 单字无强搭配
C 编者惯例   邸→やしき 与 てい 都对，gold 只是其中一种选择
```

## 溢出审计（2026-11）

「溢出」= 我们标了、gold 没覆盖的词。它全部来自散文域：

```text
歌词域   溢出 0        Uta-Net 给几乎每个汉字词都标了假名
散文域   溢出 6502     编者只挑难词标（1.6 个/行），我们标所有汉字词（10.2 个/行）
```

抽 60 条逐条核对（`tools/audit.py`，两个种子各 30 条）：

```text
正确 60 / 60 = 100%
Wilson 95% 置信区间 94.0% – 100%（60 条全对的保守下界 ≈95%）
```

结论：

```text
1. 溢出的读音基本都对——多标的是"普通词的正确假名"，不是错标
2. 散文域 precision 74.8% 是"难题口径"：只统计编者挑出来的难词，
   不能当整体精度看。按 6502×95% 折算，散文整体准确率约 91%
3. 歌词域 96.0% 是"全量口径"，可以直接对外说
```

工具：`python3 tools/audit.py --n 30 --seed 11`，产物 `eval/audit_result.jsonl`。

## 扩语料（2026-11，第二次尝试，成功）

上次用青空文庫同源语料，收益只在"上限"、成本高，撤了。这次换了思路：

```text
来源   Uta-Net 上「不属于评测集」的其他歌（按 URL 排除 dev 30 首 / test 20 首）
规模   24 首 → 810 个词形 / 2256 次出现 / 40 个多读音
产物   data/corpus/utaten_resource.json  {词形: {读音: 次数}}
规则   唯一读音且出现 ≥2 次 → 直接采信，level=A、source=resource
```

为什么这次能成：

```text
1. 域匹配——用歌词学歌词，比用青空文庫的散文语料更贴
2. 零泄漏——按 URL 排除评测用过的歌，刻意避开"在考题上学"
3. 可达——维基 dump 只有 14KB/s（387MB 要 7.5 小时），青空文庫站点被墙，
   Uta-Net 单页 6.6 秒还能抓
```

效果：

```text
资料覆盖率（ceiling）   68.4% → 79.7%   ← 天花板抬了 11.3pp
全量 coverage          82.5% → 83.5%
  歌词 DEV             88.8% → 89.0%
  歌词 TEST            88.6% → 88.8%
precision              90.5% → 90.5%（没掉）
可及 precision          93.9% → 94.2%
```

只有 24 首就把资料覆盖率抬了 11 个点，说明这条路是**可扩展的纯收益**：
每多抓一批歌，天花板就往上走一截。

扩到 49 首（1424 词形 / 4951 次出现 / 96 个多读音）后：

```text
资料覆盖率  79.7% → 83.1%
实测 coverage 不变（83.5%）  ← 增益开始递减：剩下的词要么多读音，要么我们本来就读对
precision  90.5% → 90.4%
```

又试了一条"语料读音占比 ≥80% 就强制采信"，结果 precision 掉了 1.3pp（95.9→94.6），
已撤回——语料里的读音不一定等于这句话里的读音。

## 维基 dump 语料（2026-11）

```text
来源   jawiki 分片 1（406MB，11.4 万页）
下载   单线程 14–24KB/s（4.5 小时）；16 线程分段 ~300KB/s（约 20 分钟，尾部限速）
抽取   {{ruby|漢字|かんじ}} 与 <ruby>…</ruby> 模板
产物   data/tables/resource_wiki.json —— 6168 词形 / 7636 次出现
```

接入优先级（在 `_word_decision` 里按顺序）：

```text
FORCE_READING → TRUST_TOKENIZER → 歌词语料 → 维基语料 → 多音词 → 熟字訓 → OOV → 词性
```

效果很小：

```text
资料覆盖率（ceiling） 83.1% → 84.3%
实测 coverage        83.5% → 83.6%（DEV 3140→3142 个正解，TEST 无变化）
precision            90.4% → 90.4%
```

结论：**百科语料的读音和我们已有的词典高度重合**，用到歌词上收益接近于零。
它真正能补的是专有名词/术语，而歌词里那些难读（いずこ/めしあ/ともび）属于
文艺用法，维基里本来就少。

2026-11 决定：**维基这层删掉**（`data/cache/wiki` 387MB + `resource_wiki.json` +
`build_resource.py --wiki` 模式全部移除）。要复现的话：

```bash
# 分片 1，406MB / 11.4 万页
curl -O https://dumps.wikimedia.org/jawiki/latest/jawiki-latest-pages-articles1.xml-p1p114794.bz2
# 单线程只有 14–24KB/s，务必分段并发（16 线程约 300KB/s，20 分钟）
```

教训：**语料的"领域"比"规模"重要**。同样是几十万字，Uta-Net 歌词让我们
覆盖率 +1.4pp、天花板 +14.7pp；维基百科 11 万页只换来 +2 个正解。

## OOV 对动词/形容词放行（2026-11）

做《ふざけた生活》时发现：`帰りゆく`、`争い合って` 被分词器并成一个复合动词，
词表里没有整词 → 命中 OOV → 整词弃权。但它们明明有明确读音。

```text
修法   OOV 且词性是 動詞/形容詞 → 不弃权，采信分词器读音
效果   帰りゆく → 帰[かえ]りゆく、争い合って → 争[あらそ]い合[あ]って
指标   lyrics 96.0/89.2 → 95.9/89.4（precision −0.1，coverage +0.2）
       test   94.6/88.7 → 94.5/89.0
       prose  74.3/66.8 → 74.4/67.0
```

净效果略正，且修掉的是"明明会读却弃权"的明显缺陷。

## 完整版 UniDic 对比（2026-11）

```text
来源   unidic-3.1.0.zip（用户下载，525MB → 解压 779MB）
位置   data/cache/unidic/unidic
切换   annotate.dicdir()：优先本地完整版，没有就退回 unidic-lite（该函数已随线路删除）
格式   与 lite 完全一致（26 个字段、同样的 [6]/[8]/[9]/[10]），代码零改动
```

实测结果：**指标一模一样**。

| | lite | 完整版 |
|---|---|---|
| 歌词 DEV | 96.0% / 89.2% | 96.0% / 89.2% |
| 歌词 TEST | 94.6% / 88.7% | 94.6% / 88.7% |
| 散文 | 74.3% / 66.8% | 74.3% / 66.8% |
| 片段 A / C | 11858 / 1176 | 12026 / 1008 |
| OOV 弃权 | 439 | 439（**没变**） |
| 启动耗时 | 0.37s | 0.38s |

为什么 OOV 没变：我们的 OOV 闸门查的是 **JMdict 派生的 `known.json`**，
跟分词器用哪个词典无关。换 UniDic 只影响"分词和读音"，不影响"认不认识这个词"。

结论：**完整版对当前指标没有影响**。留着不占 CPU（mmap，启动一样快），但占 779MB 磁盘。

2026-11 决定：**删掉**（`rm -rf data/cache/unidic`，779MB）。
`annotate.dicdir()` 会自动退回 unidic-lite，指标不变。（两者后来都删了）
若将来要用完整版的語種/品詞做連濁规则，把 zip 重新解压回同路径即可。

它潜在的价值在别的方向：完整版有語種（和語/漢語/外来語）、より細かい品詞，
将来做連濁/促音规则时可能用得上。

## 上下文：三条静态路都试过，全部无效（2026-11）

多音字（B 档）是当前最大的错误来源（1426 span，85.7%）。试了三种"用数据定读音"的办法：

### ① 用 NDL 语料（155 万词形）的全局频次替换读音

```text

```

**覆盖太低**（86% 的多音字凑不出搭配），且阈值降到 1 次时准确率低于现状（89.7%）。

### ③ 只统计"后接助词"

```text

n≥5:  可用 44，已对 40，能救 3，改坏 0
```

能救 3 个——**接近零收益**。

```text

```

不够格从 C 升到 B。

### 结论

```text

```

## 整词合并：子集有效，全集无效（2026-11）

错误里 20% 是"边界/部分覆盖"（世界 我们标成 世+界）。试了一条规则：

```text
相邻多段汉字拼起来是词典里唯一读音的词 → 用词典读音合并成一段
```

### 子集上很好看

```text
符合条件的 span：262
  逐段拼   对 216（82.4%）
  词典整词 对 243（92.7%）   +10.3pp
```

### 全集上是亏的

```text
              判对    判错   对齐差    coverage
不做合并      8978    726     77       88.8%
做合并        8934    720    128       88.4%
```

**判对 -44，对齐差 +51。**

### 原因：合并会吞掉相邻的词

合并的条件是"相邻汉字片段"，而这个"相邻"是**文本相邻，不是同一个词**：

```text
世界中  → 我们把 世+界+中 合成一段（因为 世界中 也在词典里）
        → gold 只标 世界，于是变成"覆盖更大词"（对齐差）
```

试过限制成"同一 token 内合并"，结果**规则一次都不触发**——
`split_pieces` 在一个 token 内本来就只产出一个汉字块，没有可合并的东西。

### 结论

```text
整词合并需要"词边界"，而我们只有"片段"。
跨词合并 = 又踩了 mixed 那个坑（分不清一个词被切开 / 两个相邻的词）。
这条规则不做。
```

## 校验器与对齐修复（2026-11）

采纳「不变量校验」的思路：**违反不是修补，是拒绝输出**。

```text
tools/invariants.py
  I1 往返一致   base 必须等于原文 [start,end)
  I2 单调有序
  I3 只含假名
  I5 纯假名不得有 ruby（数字除外）
  I6 助詞不得被覆盖
  I7 摩拉数     len(reading) ∈ [汉字数, 4×汉字数]
  I8 跨词元     必须显式声明
  I4 送り仮名   由 split_pieces 的 DP 保证，不在输出层复查
```

### 校验器立刻抓到一个真 bug

`split_pieces` 原来是贪心匹配假名块：

```text
恋煩い (こいわずらい) → [("恋煩","こ"), ("い",None)]
                       わずら 被丢掉，读音对、对齐错
```

改成 DP（求"消耗掉整个读音"的切法）后：

```text
恋煩い → [("恋煩","こいわずら"), ("い",None)]
```

泛化集因此 +0.1pp（94.4 → 94.5 / 93.6 → 93.7）。

### 政策层（--emit）

```text
--emit B   全出（默认）
--emit AB  只出 A/AB
--emit A   只出 A
```

**只是不输出，不改判定**。同一套规则核，靠档位切换产品形态。

### 一个反直觉的结论：弃权换不来精度

```text
emit=B   开发 95.9 / 94.4   留出 94.2 / 92.3   泛化 94.5 / 93.7
emit=AB  开发 95.7 / 88.5   留出 94.4 / 86.4   泛化 94.6 / 87.1
emit=A   开发 95.9 / 70.8   留出 95.5 / 71.0   泛化 94.7 / 71.5
```

**砍掉 AB 和 B（丢掉 24pp 覆盖率），精度只涨 0–1.3pp。**

原因：隐藏一档会同时删掉对的（135 个）和错的（28 个），precision 几乎不动。
**所以 emit 不是"更谨慎"，是"更少"**——它属于展示层，不是判定层。

判定层的保守已经由 C 承担（词典没答案才不标）。展示层的取舍只看用户要不要读得出来。

### 表层为键：不适用于词典查询

文章建议"规则必须以表层为键，不能以 lemma 为键"。实测：

```text
token 中 key==surface 19408（81.9%）
      key!=surface  4301（18.1%）
其中 surface 自己有语料统计的：0
```

那 4301 个是活用形（憎ん→憎む、美しく→美しい）和假名（ある→有る），
**用表层查表会全部变成 OOV**。文章说的是"ルビ边界规则"，我们没有那一层
（边界来自分词器），所以这条不适用于我们现在的 key 解析。

## A / AB / B / C 四档（2026-11）

B 档（多音字）里其实混着两类：真的两读并用，和"词典列了两个读音、实际几乎只用一种"。

## mixed 为什么收敛不了（2026-11）

`mixed` 指一条 gold 被不同档的片段拼起来覆盖。开发集 93 个，precision 76.3%。

拆开看：**86 个错的里，全部是"边界一致、读音错"**，不是边界问题。
典型是非组合读法的复合词被分词器切成两段：

```text
手提灯   gold てぢょうちん   我们 手提(てさげ) + 灯(とう)
逃路     gold みげみち       我们 逃(にげ) + 路(じ)
```

试过的收敛办法：**相邻多段汉字拼接后不在词典 → 降 B**。实测：

```text
B 档从 9.8% 涨到 13.0%，误伤 1484 个片段
```

原因：我们的输出只有片段，没有**词边界**。于是分不清

```text
手提灯（一个词被切成两段）    ← 想抓的
意味最強（真的是两个词）      ← 被误伤的
```

在片段层面这两种一模一样，所以这条规则不可实现，已撤回。

结论：mixed 是"切分粒度差"，不是规则错，留在统计里如实展示。

## 熟字訓表为什么不分表（2026-11）

`jmdict_kanjidic2_jukujikun.json`（2278 词形 / 2589 条读音）里混着两类东西：

```text
真·熟字訓    这个词的正常读音就拼不出来      大人 おとな、今日 きょう、明日 あした
生僻读法      这个词正常读音能拼，另有冷门读法  前 さき、方 さま、誰 だあれ、超 ちょー
```

**两者在数据上交叉，无法用一个判据分开。** 试过三种：

| 判据 | 结果 |
|---|---|
| JMdict 的 gikun/ateji 标记 | 只覆盖 131 / 2589 条（5%），太稀疏 |
| "有可推导读音就算普通词" | 把 身体（しんたい→可推导）和 一人（いちにん）误判成生僻类 |
| JMdict 里排第一的读音 | 不可靠：**前 的第一个读音是 さき**（不是 まえ） |

按第二种拆完实测：**只让"真"表参与判定，43 个 span 会被弃权，其中 43 个原本都标对了**
（上衣 うわぎ、梯子 はしご、一人 ひとり、七夕 たなばた、時雨 しぐれ、把手 とって）。

### 为什么 derivable 只能判一半

```text
derivable(word, reading) 能回答：这个读音能不能按字的音訓拼出来
                        不能回答：这个词是不是熟字訓词
```

因为一个词可以同时有"可推导读音"和"熟字訓读音"：

```text
身体  しんたい（可推导） / からだ（熟字訓）
一人  いちにん（可推导） / ひとり（熟字訓）
```

**判别的是读音，不是词。** 所以表天然混着两类，规则只能在"读音"这一层分流。

### 现在的分流方式（不改数据，改规则）

```text
读音能按字拼出来  → 直接放行，表里的冷门读法不参与
拼不出来          → 必须在表里，否则弃权
```

效果等价于"把表拆开用"，但不需要动数据，也不会误伤上面那 43 个。

**决定：保持一张表。** 以后如果又有"要不要把熟字訓表拆开"的念头，先看这一节。

## 切分校验：拼接后对词典（2026-11）

分词器会把一个词切成几段（日曜+日、入道+雲、飴+細工），拼回来的读音常常是错的：

```text
日曜日  分词 日曜+日      我们 にちようひ   词典/正确 にちようび
入道雲  分词 入道+雲      我们 にゅうどうくも 词典/正确 にゅうどうぐも
飴細工  分词 飴+細工      我们 あめさいく    词典/正确 あめざいぐ
不器用  分词 不+器用      我们 ふきよう      正确 ぶきよう
```

做法：相邻汉字片段拼接（2–6 字），若在 `jmdict_kanji_compounds` 里且拼接读音 ≠ 词典读音，
**整串弃权**（reason = `segmentation`）。

```text
lyrics      96.1/94.4 → 96.5/94.3
lyrics_test 94.4/92.1 → 94.7/92.0
prose       74.0/69.1 → 74.9/68.9
启动        0.18s → 0.24s（多读一张 4.5MB 表）
```

冲突时的处理：

```text
词典唯一读音 → 采用（22 处：对 18、错 4）
词典多读音   → 弃权（6 处）
```

两个版本的对比：

```text
              弃权版          采用版（现行）
lyrics      96.5/94.3      96.4/94.6
test        94.7/92.0      94.6/92.1
prose       74.9/68.9      74.7/69.4
```

采用版 coverage +0.3~0.5、precision -0.1~0.2。选了采用：
这类冲突里我们的拼接本来就是错的（词典对 82%），空着不如给出词典读音。

## 对标 EZFurigana 的四层架构（2026-11）

EZFurigana 公开的架构（[精度页](https://www.ezfurigana.com/furigana-accuracy)）：

```text
1  Sudachi 分词      词边界、原形、词性、候选读音
2  扩充词典          复合词、领域词、固定表达、缺失读音
3  规则层            助数詞、助詞、接尾辞、惯用句、連濁、固定短语覆盖
4  ModernBERT 兜底    只对"真歧义"的词调用
```

原则：**词典优先，规则其次，上下文模型只在需要时用。**
它报 98.8%（7500 行，跨新闻/文学/网文/维基/社媒/字幕/庭审），
同集 Sudachi 94.6%、MeCab 93.9%。

对照我们：

| 层 | EZFurigana | 我们 |
|---|---|---|
| 分词 | Sudachi | UniDic（fugashi） |
| 词典 | 扩充词典 | JMdict 六表 + glossary |
| 规则 | 助数詞/助詞/接尾辞/惯用句/連濁 | 助数詞 + 音便 + 熟字訓/专名/OOV 闸门 |
| 上下文 | ModernBERT 兜底 | 无 |
| 承认的极限 | 人名地名、連濁例外、长尾 | 同类 |

结论：

```text
· 分层方向一致，说明架构没错
· 差在第 3 层的"惯用句/固定短语"，和第 4 层的"兜底"
· 第 4 层要等第 3 层补齐才有意义——它们自己也说模型只覆盖"真歧义"
· 我们的评测只有两个域（昭和文学 + 歌词），论泛化比它窄得多
```

## 规则分两套：确定 / 不确定（2026-11，已被上一步取代）

判定链拆成两类。**确定规则默认常开；不确定规则默认关闭，可整套接入。**

| ID | 规则 | 类别 | 判据 |
|---|---|---|---|
| R1 | 语料表唯一读音 | **不确定** | 我们 49 首歌的抽样，不是词的性质 |
| R2 | 人工钉死读音 | 确定 | 显式覆盖，不做推断 |
| R3 | 白名单采信分词器 | **不确定** | 手选的 19 个词 |
| R4 | 多音词只看首选 | **不确定** | JMdict 条目顺序，不是词频 |
| R5 | 熟字訓允许集 | 确定 | 读音是否在词典记录的集合里 |
| R6 | 词表外弃权 | 确定 | 词表里没有这个词 |
| R7 | 固有名詞弃权 | 确定 | 读音不可推 |

接入方式（三选一）：

```bash
python tools/annotate.py --rules R1,R3,R4 --stdio
NHONGO_RULES=R1,R3,R4 python tools/annotate.py --stdio
echo '{"enable":["R1","R3","R4"]}' > data/curated/rules.json
```

响应里的 `version.rules` 会写明实际启用的集合，可追溯。

### 代价（实测）

```text
                    只开确定（默认）        全部接入
lyrics              95.9 / 94.2            96.0 / 93.5
lyrics_test         94.2 / 92.0            94.5 / 91.0
prose               73.3 / 68.0            74.4 / 67.0
```

两套几乎打平：默认 coverage 反而略高（R4 会主动弃权），precision 低 0.1–1.1pp。
所以"只开确定规则"不是明显变差，是**用一点点 precision 换每条规则都能说清**。

### 拆规则时顺带修的一个 bug

R4 关掉后暴露出：熟字訓的"允许集"只装了熟字訓那几条读法（前→さき、身体→からだ），
普通读法（まえ、しんたい）不在里面 → 一批常用词被误判成"熟字訓冲突"。

修法：允许集 = 熟字訓读音 ∪ 词典记录的全部读音（`heteronym[key]`）。
以前 R4 排在前面，把这些词拦下来了，所以 bug 一直没暴露——**规则链变简单时，
旧规则里的假设会现形**。

## 固有名詞规则收紧（2026-11，**已回滚**）

测歌时发现 `固有名詞` 一律弃权会误伤 `春日｜関西｜三股` 这类普通词。
试过"只弃词表外的"：

```text
指标   lyrics 95.9/93.7  test 94.5/91.1  prose 74.4/67.3（覆盖率 +0.1~0.3）
结果   関西→かんさい ✓
       三股→みまた   ✗（应 さんまた）
       春日→かすが   ✗（应 はるひ）
```

**回滚了。** 理由不是指标，是可解释性：

```text
旧规则   "固有名詞 → 不标"            —— 一句话说清，能预测
新规则   "固有名詞且不在词表 → 不标"  —— 为什么 関西 标、三股 不标？
                                        答：JMdict 里恰好有没有它
```

"在不在词表"是运气，不是关于这个词的任何性质。用它当判据，
系统就多了一条无法解释的规则，换来 +0.2pp coverage 和一堆错读。

**教训**：一条规则如果不能一句话说清"什么时候成立、为什么"，
它迟早会以难查的方式出错。宁可少一条规则，不要多一条说不清的。

## 关键决策

### 1. 评测口径：gold 是"人工选择标注"，不是全量

最初把「我们标了、gold 没标」算成错误，precision 只有 21.5%。
但 Aozora/Uta-Net 的 ruby 是编者挑出来的（通常只标难词），不代表其他词不该标。

改成：

```text
precision = 判对 / (判对 + 判错)      只在 gold 覆盖处可验证
溢出      单独计数，抽样人工看，不计入 precision
对齐差    我们标的词比 gold 大/小（读音不冲突），单独计数
```

### 2. 读音字段：用「表记读音」而不是「发音」

UniDic 的 `[9]発音形出現形` 会把长音写成 ー（`こくー`），而 gold 用 `こくう`。
改用 `[6]語彙素読み` 并按 `[8]/[10]` 的活用差异调整，一次把长音类错误清掉：

```text
precision 77.4% → 89.3%
```

### 3. 送り仮名：按「假名块」对齐，不是首尾剥离

只处理首尾假名时，`抱きしめ`（中间夹假名）会被标成「抱きしめ→だきしめる」。
改成：汉字块 ↔ 假名块交替切开，在读音里依次定位假名块，中间那段归汉字块。

```text
抱きしめ → 抱(だ) + きしめ(K)       ← 正确
枯らし   → 枯(か) + らし(K)
```

### 4. 三张表从 JMdict 自动抽，不手工抄

`tools/build_tables.py`：

```text
熟字訓   ① JMdict 的 gikun/ateji 标签  ② 读音无法由各汉字音训拼出（DFS 判定，允许连浊/促音）
多音词   同一汉字形有 ≥2 个常用读音
已知表   全部汉字形，用于 OOV 检测
```

规模：熟字訓 2278 条、多音词 2269 条、已知词形 22.7 万。
只有「常用」的 (形,读) 对才进熟字訓，避免 `大人=うし` 这种 JMdict 里的生僻异读干扰。

**光靠词典 + 表，precision 天花板约 90–91%。**

## 评测集上限的测法（`make ceiling`）

被"precision 只有 90%"困扰过一阵，后来想清楚要拆开看：

```text
误差 = 资料里根本没有这个读音（评测集天花板） + 资料里有但我们选错（方法问题）
```

跑出来的结论：

```text
4746 个 gold span 里，1488 个（31.4%）的读音不在 UniDic/JMdict/熟字訓表的任何一处
→ 任何词典方法对这些无能为力，coverage 上限就是 68.6%
→ 在"资料里有答案"的 3258 个 span 上，我们的 precision 是 92.5%
→ 365 处标错里，166 处是方法问题，199 处是天花板
```

这个拆分成了后续所有优化的坐标系：
**改方法看"可及部分 precision"，扩语料看"资料覆盖率"**，两者不要混着看。

```text
资料覆盖率   68.6% → 74.1%     ← 天花板确实抬了 5.5pp
实际 coverage 59.8% → 59.6%    ← 没动，甚至略降
precision    88.6% → 89.2%
```

为什么撤：

```text
1. 收益在"上限"，不在当前输出——多出来的覆盖里，多读音词居多，遇到就弃权
2. 下载成本高：120 部要 40 分钟，失败率高（大文件超时）
3. 真正卡脖子的是"资料里根本没有"的那 31.4%（卓子→てーぶる 这种），
   扩青空文庫同源语料救不了——得换来源（Wikipedia/NDL）或上模型
```

脚本和数据已删；将来若要抬高天花板，重做时优先换语料来源而不是加量。

## 外部方案调研（2026-11）

### JRM：候选约束 + 文脉 reranker（最贴近我们的问题）

- 文章：<https://zenn.dev/nixo/articles/3139042d4034f2>
- 演示：<https://jrm-demo.2-38.com/>
- 结构：词典/形态素 → **读取候选格（lattice）** → ModernBERT-Ja reranker → 置信度 → 低置信回落词典读音

关键数字（作者自测）：

```text
难读测试 66 问        100%（既有最强引擎 60.6%）
独立评估 260 问       91.9% vs 61.9%
加难 942 问           77.0%（同形异音语 81.9%、数词日期 63.1%、固有名詞 61.7%、IT 用语 77.8%）
```

对我们最重要的三条：

1. **不让 LLM 自由生成，只在候选格里选** —— 这正是我们 M3 的设计，且他们证明这条路有效
2. **每个 token 带 confidence 和来源**（reranker / 词典 / 用户词典）—— 我们的 A/B/C 分级可以直接用
3. **难读语料来自国会图书馆的振假名语料**（公有领域），不是手工标

### 大规模振假名标注语料

- 论文：<https://www.jstage.jst.go.jp/article/jnlp/33/3/33_1698/_article/-char/en>
- 国会图书馆的振假名语料，公开、可用于训练/评测
- 对我们：可以把 gold 从 40 部青空文庫扩到十万级，且标注质量更高

### PACLIC 2025：浏览器内可跑的字级读音推定

- 论文：<https://aclanthology.org/anthology-files/pdf/paclic/2025.paclic-1.44.pdf>
- 面向教育场景，按学习者等级控制汉字难度
- 对我们：如果以后要"按级别只注 N5-N3 的汉字"，可直接借鉴

### 一个现实校准

连专门训练的 130M 模型在"加难 942 问"上也只有 77%。这说明：

```text
"任意文本、全部汉字、读音全对" 不存在
可行的目标只能是：高置信的标，低置信的不标
```

我们设计里的 99.5% precision 是对**已标注部分**的要求，不是对全文的要求——
这个区分必须一直守住。

## 为什么不能直接用 kakasi 做标注（2026-11）

同一套 gold（歌词 3 集 + 散文，4051 行）上做整行假名对比：

| | 整行完全一致 | 字符级 |
|---|---|---|
| pykakasi（kakasi 的 Python 版） | 61.3% | 42.8% |
| 本引擎 | 70.3% | 44.9% |

口径：把 gold 的每个 span 替换成它的读音拼成整行假名，与工具输出的整行假名
逐字比较；片假名统一折成平假名、去标点。**这个口径比"词级 precision"苛刻**，
所以两边数值都远低于平时报的 95%。

kakasi 的典型错误（都是"要看上下文"的地方）：

```text
君        → くん   （应 きみ）
望み通り   → のぞみとうり（应 どおり，连浊）
何でもない → なんで  ✓（分词对了）
```

结论：

```text
kakasi 是"表驱动 + 最长匹配"，能答"这词通常读什么"，
答不了"这句话里该读哪个"。
静态查表在词级大约 90%，我们多出来的 5 个点靠：
  语料读音分布定档（A/AB/B）+ 弃权（C）+ 分词对齐（DP）
差的就是最贵的那 5 个点。
```

## Unicode 归一化：看起来一样的字符串，其实是两个（2026-11）

**症状**：明明重新抓到了正确歌词，列表里还是显示旧的错误匹配；
同一首歌有时匹配成功、有时失败。

**原因**：日文浊音有两种写法——

```text
预组合   ぎ = U+304E              （一个字符）
分解     き = U+304D + ゛=U+3099   （两个字符）
```

肉眼完全一样，`==` 却是 False。缓存键是 `md5(title|artist)`，
于是同一个名字算出两个键：

```text
抓取时用 A 种写法写入 cache/<keyA>.json
列表查询用 B 种写法去读 cache/<keyB>.json → 找不到 → 显示"没歌词"或旧结果
```

**修法**：

```text
lyrics._key()   计算 md5 前先 unicodedata.normalize("NFKC", …)
lyrics._norm()  比较歌名前也 NFKC（大小写已经在做）
tools/migrate_cache_keys.py   一次性把旧键文件改名到新键（本次迁移 100 个）
```

**教训**：

```text
· 任何进入"键 / 比较 / 索引"的字符串，先归一化（NFKC + casefold）
· 中文/日文/韩文输入法产生的文本尤其容易混入分解形式
· 归一化上线时必然让旧缓存键失效 → 同时准备迁移脚本，否则会"丢歌词"
```

**当时的规模**：未迁移前库从 340 掉到 266（74 首要靠旧键才找得到），
迁移后恢复 340。

## 重写/拆模块时的两个反复踩的坑（2026-11）

这一轮重构里同一个错误犯了四次，都是"代码能跑、功能是死的"：

### 坑一：整块替换把同区域的方法一起删了

```text
重写 server.py 的辅助方法区段时，用"从 A 到 B 整段替换"
→ 只保留了新写的 _pl / _import_to_list / _lazy_match，
  同一区段里的 _rematch / _edit / _pick 一起消失
→ 前端点「重新匹配歌词」直接 500（连接被断开，浏览器看到的是"没反应"）
```

```text
对策：替换一个区段前，先列出该区段里定义的所有符号，逐个确认去向
      grep -n "^    def \|^def " 区域首尾之间
```

### 坑二：拆模块后漏导出名字

```text
lyrics.py 拆成 text / cache / fetch 三个模块 + 门面后：
  · CFG 没在门面导出      → _rematch 抛 AttributeError
  · TS（TIMED 的旧名）没带过去 → get_lrc 抛 NameError
  · JP 没导出             → 导入即报错
  · lyrics_cache 的 CACHE 被错误地指向 data/cache（少了一层 lyrics）
    → 表现是"579 首里只有 3 首有歌词"，极难从现象联想到路径
```

```text
对策：拆分后用一段脚本做"未定义名字"粗检，界面上还有冒烟测试兜底
      路径常量这种"看起来没问题"的最危险：它不报错，只是找不到文件
```

### 为什么单测没挡住

```text
· 单元测试只 import 它用到的那几个函数，漏掉的部分照样能跑
· 界面冒烟测试才能抓到 ReferenceError / 空列表 / 点了没反应
→ 结论：动前端或删方法时，必须跑 tests/test_ui_smoke.py
```

## 文件锁：两个进程抢一个 json（2026-11）

```text
现象：默认歌单从 579 首变成 0 首
原因：浏览器服务（8766）和桌面 app（随机端口）同时开着，
      各自 load → 改 → save playlists.json，后写的覆盖前者
修法：playlists.py 的写操作全部包进 fcntl.flock（跨进程互斥）
     另外 build() 不再"清洗"找不到的 uid，避免一次误读把内容删掉
```

```text
一般规律：只要数据存在"两个进程都能写"的文件里，就必须加锁；
         只读的缓存（歌词）可以不加，最坏是重复抓一次
```

## 播放栏显示 "Error"：音频接口方法被删（2026-11）

**症状**：点歌之后，下方原生播放条显示 `Error`，歌词正常但没有声音。

**原因**：这次"整块替换 server 辅助方法"时，`_get_audio` 也被一起删掉了。
`/audio/<idx>` 抛 AttributeError → 连接直接断开 → 浏览器 `<audio>` 收到 0 字节
→ 原生控件显示 `Error`。

```text
现象（播放条 Error）和原因（Python 方法不存在）隔了三层：
  前端看是"音频加载失败"，日志里却是 AttributeError
```

**排查手法（这次有效）**：

```text
在窗口里读 audio 的状态而不是猜：
  au.error.code      4 = MEDIA_ERR_SRC_NOT_SUPPORTED（其实就是 404/空响应）
  au.readyState      0 = 一个字节都没读到
  au.currentSrc      确认请求的是 /audio/<idx>
然后用 curl 直接打这个 URL：返回 000/空 → 服务端挂了
```

**修法**：补回 `_get_audio`，并保留 Range 支持（否则拖动进度条失效）。
验证：`/audio/2` 返回 200 + 4.9MB；带 `Range: bytes=0-1023` 返回 206。

```text
教训：只要前端出现"媒体/资源类 Error"，先 curl 那个 URL，
      不要从浏览器行为反推——它只会告诉你"加载失败"。
```

## LRC 编辑器：设计动机与放弃的方案（2026-11）

> 现状见 [`lrc-editor.md`](lrc-editor.md)。这里只留"为什么这样、为什么不那样"。

### 为什么想用人声波形

```text
原曲波形里间奏、鼓点、长音都像"句首"，副歌反复时几乎没法手动对齐
人声波形只有唱的地方有起伏，句首句尾一眼可见
→ 设计上写"人声优先，按需分离，没有则原曲兜底"
→ 实际没接 demucs（100MB 模型 + 每首 1–3 分钟），先用原曲波形
```

### 为什么不做自动打轴

```text
理由一  歌词和音频的对应本身不可靠（重复段、间奏、念白），自动结果要人工复核
理由二  Whisper / 强制对齐对日语音节的边界误差在 100ms 量级，正好是打轴容差
理由三  手动打轴的真实成本是"每首 3–5 分钟"，自动打轴+复核并不更快
结论    先把手动路径做顺（点波形 → 点行、键盘、整体偏移），自动留到以后
```

### 早期设计稿里、后来被简化掉的

```text
· 工具条一行 + 导出到…        → 现在是三行工具行 + 另存为 + 导入 LRC
· 保存前弹确认框校验           → 改成实时保存 + 界面提示，不打断
· 波形画 0.5 秒刻度 + 每秒数字 → 太花，改成只画每句起点线（暖橙色）
· 缩放 1–60 秒                 → 改成 2–10 秒（5 秒最常用）
· 波形固定不可滚动              → 改成跟随播放、暂停冻结、可关跟随
```

### 已定的选择（当时拍板，现在仍成立）

```text
① 波形高度 120px
② 原地保存 + 单份 .lrc.bak，"恢复最初"回到它
③ 行内注音 漢字(かな) 当普通文本，原样读写
④ 整体偏移手动按钮（±0.1 / ±0.5），只影响播放，不改文件
⑤ 不做自动打轴
⑥ 不把编辑器做成独立页面（和播放共用一套时间语义）
```
