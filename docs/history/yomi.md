# yomi：日语标注引擎设计

> **定位**：日语标注引擎（现在以桌面播放器为唯一前端）。输入任意日文，输出三层标注——
> **振假名（ruby）/ 罗马音（romaji）/ 键盘键位（ime keys）**，并利用上下文消歧。
> 任何客户端（桌面应用、脚本、其他机器）通过 HTTP 或 stdio 调用。
>
> **本文要解决的核心问题**：不设人工复核，怎么保证标出来的读音是对的？
> 答案是把"人工复核"从流程里彻底移除，用三件事替代：**发布前评测 / 运行时敢放弃 / 出错不显眼**。
>
> 前提：任意输入（不是固定语料）；首要场景是歌词翻译；准确性优先于速度；实时为可选项。

**当前状态（2026-11）**：三层都已实现——振假名（Sudachi + 4 张表 + 规则链）、
罗马音、键位；

本文不再重复，避免两处数字漂移。
```

## 0. 一页摘要

```text
问题    没有人工复核，怎么保证标出来的读音是对的？
答案    不保证"都标对"，而是保证"标出来的都对"，其余不标。

三条支柱
  1. 发布前评测   用金标准语料把指标标定住；退化就拦发布
  2. 运行时敢放弃  只有"引擎不认识"和"切不出来"才弃权；其余一律标，用档位表达不确定
  3. 出错不显眼   默认外观就是"没有假名"；中置信用淡标；可选点词查询

目标     precision ≥ 99.5%，coverage ≈ 85%（够用即可）
现状     见 docs/eval.md（歌词三集与散文的 precision/coverage）
不做     人工复核队列、用户纠错流程、在线学习、歌曲级缓存（v1）

三个输出层（同一份读音派生，不可混用）
  ① 振假名   汉字 → 假名，逐字或整词            ← 上游，正确性决定一切
  ② 罗马音   逐字转写（は→wa、きょう→kyou、コーヒー→ko-hi-）  ← 依赖 ①，确定性派生
  ③ 键位     IME 输入序列（は→ha、を→wo、ー→-）              ← 依赖 ①，确定性派生

已定决策
  D1 和語多音词上 LLM 消歧（只在候选里选，不生成）
  D2 固有名詞标 B 档（淡色），不弃权——弃权等于白扔 73.8% 的正确率
  D3 歌曲级缓存放 v2
  D4/D5 独立进程，部署在服务器或本机，不做手机端
        （stdio + 本地页面已实现；单机 HTTP 服务由桌面 app 内置）
```

首要原则：**正确性 > 精度 > 覆盖率**。泛化优先于跑分——评测集涨点但只在
那几十首歌上成立，不算进步（见 `docs/NOTES.md` 总原则）。

关键取舍的一句话：**覆盖率是可以让的，准确率不能让**。少标 15% 的汉字，在日语排版里是正常现象；标错 0.5% 的读音，用户会把它当知识记住。

## 1. 约束与判断

### 1.1 场景约束

| 约束 | 影响 |
|---|---|
| 任意输入（歌词、对话、抓取文本） | 不能靠预计算索引，必须运行时分析 |
| 面向他人 | 没有可信的反馈闭环；不能假设用户会发现错误 |
| 准确性优先 | 可以容忍 10–50ms/行，甚至整首 1–2s |
| 歌词为主 | 行短、上下文少、当て字/造語多、常有英文与片假名 |
| 实时可选 | 需要一套"快但保守"的通道 + 异步精修 |

### 1.2 两种错误的代价不对称

| 错误 | 用户感知 | 后果 |
|---|---|---|
| 漏标（有汉字、无假名） | 无感，日语排版里常见 | 损失一点学习价值 |
| 标错（假名与读音不符） | **无感，且会信以为真** | 用户学到错的读音，我们还不知道 |

因此目标函数不是"标注尽可能多"，而是：

```text
maximize coverage   s.t.  precision ≥ 99.5%
```

### 1.3 为什么人工复核不可行

```text
1. 用户不具备判断力     他不会念这个词，正是他需要假名的原因
2. 规模不匹配          任何"逐条确认"的设计都会把使用成本推给最没有能力的人
3. 没有动机            纠错对用户没有即时收益
4. 复核者缺席          你不是运营方，无法提供 7×24 的标注团队
```

结论：**凡是需要用户参与才能正确的环节，都不能进入主流程**。

### 1.4 已定决策（v1）

| 编号 | 决策 | 理由 |
|---|---|---|
| D1 | 和語の多音词**上 LLM 消歧**（只作用于 B 档） | 生/上手/今日 这类靠词典定不了；LLM 只在候选里选，不生成。实测 B 档 73.2% → 80.7% |
| D2 | 固有名詞（人名/地名/组织/作品/品牌）**标 B 档**，不弃权 | 读音无规律（日本橋 にほんばし/にっぽんばし）；但实测专名读音 73.8% 正确，弃权等于白扔 |
| D3 | 歌曲级缓存**本版不做** | 先保证单次标注正确；缓存是后续优化，不进入 v1 设计 |
| D4 | 做成**独立进程**，任何客户端都能调用 | 桌面应用、脚本、其他机器共用同一个标注服务 |
| D5 | 部署在**服务器或本机**，不做手机端 | 去掉移动端约束，引擎可以用重量级方案 |

D4/D5 的连带影响（贯穿全文）：

```text
1. 引擎可以是 Python 进程（Sudachi），不受"不能 fork"的限制
2. 可以用 mmap：词典文件映射，私有内存 100–200MB，压力下可回收
3. 进程边界 = 天然可被多种客户端调用，前端只管渲染，不背词典
4. 接口必须版本化：词典/规则升级不能悄悄改变客户端看到的语义
5. 评测与生产用同一个进程、同一份词典（不再有"两套引擎对不齐"的问题）
```

### 1.5 固有名詞的界定与判定

定义：指代**特定**对象（不是某一类）的名词。歌词里经常出现，且读音不可推。

| 类别 | 例 |
|---|---|
| 人名 | 山田太郎、さくら、米津玄師、KOKIA |
| 地名 | 渋谷、北海道、日本橋、大阪 |
| 组织 / 团体 | 乃木坂46、B'z、東京事変 |
| 作品 / 品牌 | 鬼滅の刃、Yahoo!、Toyota |
| 事件 / 节日 | 紅白歌合戦、夏祭り（边缘） |

为什么不能猜：

```text
日本橋   にほんばし（东京）/ にっぽんばし（大阪）
明日香   あすか（人名）/ あしたか（地名）
米津玄師  よねづけんし
B'z      ビーズ
```

判定方式（不需要人工）：

```text
1. 形态素品詞   Sudachi 的「名詞-固有名詞-人名/地名/組織」细分
2. 启发式      OOV + 片假名长串、OOV + 拉丁字母串
3. 随包词表    你确认过的专名进词表 → 之后按 A 级正常标注
```

对应策略（D2）：命中 1 或 2 且不在词表 → **B 级（淡标）**；在词表 → A 级正常标。

实测：能对上 gold 的专名 65 个，读音对 48 个（73.8%）——比弃权有价值。

## 2. 支柱一：发布前评测

把"人"从运行时移到发布前——你在自己的电脑上决定阈值，用户端只是执行。

### 2.1 金标准语料从哪来

实际用到的（2026-11）：

| 来源 | 内容 | 规模 | 许可 | 状态 |
|---|---|---|---|---|
| 青空文庫 ruby 版 | 人工标注的经典文学 | 40 部 / 742 条 / 1173 span | 原文公有领域 | ✅ 主力散文集 |
| Uta-Net 歌词页 | 站点编辑标注的振假名 | 50 首 / 2170 条 / 5901 span | 站点内容，仅本地使用 | ✅ 歌词集（30 开发 + 20 留出） |
| 手工构造 | 数字/专名/当て字/拉丁混排 | 49 条 | 本项目 | ✅ 补稀有规则 |

试过但没留下的：

| 来源 | 结果 | 原因 |
|---|---|---|
| 日语维基 ruby dump | 1 分片 / 11 万页 / 6168 词形 | 与词典高度重合，只多 2 个正解 → 已删 |
| 青空文庫非评测作品（做语料） | 28 部 / 1135 词形 | 收益只在上限，实测 coverage 反降 → 弃用 |
| 常用漢字表付表（116 条熟字訓） | 未使用 | 改为从 JMdict 机械抽取（2278 条，覆盖更广） |

原则：**评测集必须包含"看起来像真实输入"的脏数据**——歌词里就有英文、卢恩字母、
古语假名遣（`云フ`）、标点夹数字（`一、二`）。

### 2.2 指标定义

**实际实现**（`tools/evalkit.py` 的 `score()`）：

```text
对齐方式   gold span 与预测 segment 按字符区间重叠
           落在同一个 gold span 上的多个预测段会先拼接再比读音
           （掃除+機 拼成「そうじき」能和 gold 的 掃除機 对上）
规范化     NFKC + 片假名→平假名

precision = 判对 / (判对 + 判错)      分母只含 gold 覆盖到的预测
coverage  = 判对 / gold span 总数
溢出      预测了但 gold 没覆盖 —— **不计入 precision**，单列并抽样人工核对
漏标      gold 有、我们没标（对齐差另列：覆盖范围不同但读音不冲突）
```

为什么不用"已标注 / 应标注"：**gold 是选择性标注，不是全量**。
散文里 Aozora 编者平均只标 1.6 处/行，我们标 10 处/行；
若把"我们标了 gold 没标"算成错，precision 会被压到 21%（验证过）。

必须分开看的分桶（`make stats` / `make eval-real` 都会给）：

```text
R1  基线（不含其他特殊规则）
R2  送り仮名切分        R3  音便        R4  熟字訓
R5  多音詞              R6  数字助数詞   R7  固有名詞
R8  当て字              R9  假名直通     R10 片假名
R11 拉丁/数字混排       R12 熟語切分
域：lyrics（开发/留出）、prose
```

### 2.3 阈值怎么定（设计，当前**未实现**）

原设计是靠 confidence 扫阈值。**现在的实现没有 confidence 数值**，
用的是"规则链 + 分档"：有依据就标，用 A/AB/B 表达把握程度，只有"没依据"才弃权。

下面是原设计的思路，保留作为后续目标：

```text
1. 让流水线对每个 token 输出 confidence ∈ [0,1]（多信号加权）
2. 从高到低扫阈值 t：在 confidence ≥ t 的子集上算 precision / coverage
3. 取满足 precision ≥ 99.5% 的最大 coverage 对应的 t
4. 把 t 写进发布配置；同时记录该点的 coverage 作为基线
```

当前替代方案（已实现）：弃权规则表（见 §3.3）+ 弃权原因统计（`make stats`）。
实测各原因的"硬标正确率"：非首选读音 59%、数詞 77%、OOV 35%、固有名詞 26%
——这就是"为什么该弃"的量化依据。

### 2.4 发布门禁

```text
> 现状：**没有门禁，只看指标**（2026-11 决定）。下面是概念上的"发布标准"，
> 靠人工对照 `make eval-real / eval-test` 的数字判断，不做自动断言。

必过
  precision ≥ 99.5%（总体 + 和語桶 + 数字桶）   ← 当前 95.2（开发）/ 74.9（散文），未达标
  拉丁/数字/符号 passthrough 100%
  熟字訓表回归 100%（我们用 JMdict 抽取的 2278 条，不是官方 116 条）
  coverage 不低于上一版基线 - 2%
禁止
  为了提 coverage 而放宽阈值
  新增规则后不跑评测
```

### 2.5 评测本身的局限（必须承认）

```text
语料偏置     青空文庫偏文学，歌词偏口语与造語 → 歌词单独建集
标注不一致   金标准本身有争议（例：今日は 的读音）
长尾         低频词在语料里样本极少，评测结果不可信 → 只当参考
```

## 3. 支柱二：运行时敢放弃

### 3.1 输出分级（A / AB / B / C / K）

| 级别 | 触发条件 | 输出 | 实测 precision |
|---|---|---|---|
| **A** | 语料 ≥99% 只读一个音（n≥20）；或不在统计表里 | 正常 ruby | 96.2% |
| **AB** | 多读，且读音 == 语料主读 | 略淡 ruby | 91.7% |
| **B** | 多读但≠主读 / 无统计 / 固有名詞 / 数字 | 淡色 ruby | 73.4% |
| **C** | OOV / 对齐失败（只有这两种） | 原文照排 | — |
| **K** | 该段本来就是假名 | 无 ruby | — |

政策层（`--emit A|AB|B`）只决定"输出到哪一档"，不参与判定。
注意这**不是**"宁可少标"的延伸——判定层的保守由 C 承担（词典没答案就不标），
展示层的取舍只有一个依据：用户要不要读得出来。

```text
emit=B   全出              开发 95.2 / 94.4
emit=AB  只出 A/AB          开发 95.7 / 87.2
emit=A   只出 A             开发 95.2 / 73.8
```

曲线几乎是平的，这不奇怪：隐藏一档会同时损失对的和错的，
所以精度不动、覆盖率掉——**它不是"更谨慎"，只是"更少"**。

（数字来自歌词开发集 3372 个 gold span）

档位只看**语料读音分布**（`data/corpus/ndl_reading_stats.json`）：

```text
share ≥0.99（n≥20）  → A    事实上只有一个读音
读音 == 主读          → AB   有歧义，但语料支持我们的选择
其余                  → B    有歧义，语料不支持
不在统计表            → A（引擎单读）或 B（heteronym 里有多读但没统计）
```

专名和数字单独进 B：它们有读音，但不可推。

```text
data/corpus/ndl_reading_stats.json   1294 个词的 {主读, 样本数, 占比, 分布}
```

为什么分三档而不是两档：B 里混着"真两读并用"和"词典列了两读、实际只用一种"。
语料统计能把后者升到 A 或 AB——实测四集合计的 precision 是 96.3 / 91.7 / 72.9，梯度清楚。

C 与 K 必须分开：前者是"不敢标"，后者是"不需要标"。

### 3.2 置信度信号（六个，可组合）——**未采用，改用语料分布**

> 现状：没有 confidence 分数。A/AB/B 三档由**语料读音分布**决定（§3.1），
> 不是六个信号加权。下面保留作为演进方向。

```text
S1 候选数       词典给出的读音候选数量；1 个 → 强信号
S2 词表命中     熟字訓 / 助数詞 / 随包高频词表 → 最强
S3 多源一致     两个分析器对同一段的读音是否相同（现只有 Sudachi，无第二源）
S4 词频         语料里的读音分布（ndl_reading_stats.json）——实际在用的就是这个
S5 上下文规则   助詞接续、量词搭配
S6 LLM 一致     仅对 S1–S5 判定为中置信的 token 启用
```

### 3.3 判定规则（只剩确定规则）

2026-11 把"不确定"的两层（词组查词典、切分采用词典读音）整层删除了。
现在每一步的判据都是"这个词或这个读音本身的性质"：

| 顺序 | 规则 | 判据 | 结果 |
|---|---|---|---|
| 1 | glossary_lyrics.json（5 条） | 人工确认过读音（**只为歌词领域调过**） | A（`forced`） |
| 2 | 数字 | 读音取决于后接的助数詞 | B（`numeral`） |
| 3 | OOV | Sudachi 的 `is_oov()` 为真 | C；带送り仮名且切分成立则放行 |
| 4 | 固有名詞 | 词性为专名 | B（`proper`） |
| 5 | 默认 | 采信引擎读音 | A / AB / B（`dict`，见 §3.1） |
| 6 | 助数詞 | 数字＋助数词（带音便） | A（`counter`）；数词＋日 → B |
| 7 | 不变量 | 违反任一不变量 | C（不修补） |

已删除的层（都实测过，见 `docs/NOTES.md`）：

```text
词组层      含假名词组查词典 → 用词典读音       收益 +0.2~0.8pp，但会扩边界
切分采用    纯汉字串拼接对词典 → 采用/弃权      收益 +0.3~0.9pp，但会用古语读法
熟字訓表    读音在允许集里就是"没读错"≠"读对"   82.9%，比多音词还低
known 词表  22.7 万词表做 OOV 闸门              换成 Sudachi 的 is_oov() 更准
整词合并    相邻片段拼成词典词 → 用整词读音      子集 +10pp，全集 -44（吞掉邻词）
```

### 3.3.1 档位只有一个赋值点

```text
_word_decision()   只说"这个读音怎么来的"（source）和"是否弃权"（abstain）
assign_level()     唯一的档位判定点：source + 语料统计 → (level, basis)
```

输出的每个片段带四个字段：

```json
{"base": "何", "ruby": "なん", "level": "AB", "source": "dict",
 "basis": "与语料主读一致（なん, n=1086）", "word": 3}
```

- `source` 证据来源（forced / counter / jukujikun / dict）
- `level` 档位（A / AB / B / C）
- `basis` 一句话说明凭什么（如 `与语料主读一致（おとな, n=16）`）
- `word` token 序号——用来判断哪些片段属于同一个词

### 3.4 LLM 的角色：只做选择题，不做填空题

```text
允许   给 LLM「候选列表 + 上下文」，让它选一个
禁止   让 LLM 直接给读音
原因   模型会编出看似合理但不存在的读音（絆 → ほだし），
       而这类错误恰好是用户最无法识别的
```

配套纪律（**已实现**，`--llm` 默认关闭）：

```text
只碰 B 档          A 档 96% 以上，LLM 进去大概率改坏；C 档没有候选
候选约束           返回的读音必须在候选集合里，否则当没问
候选来源           词典读音 ∪ 语料主读 ∪ 多音字表（≤8 个）
离线预取           结果落 data/cache/llm/choices.json，评测时不联网
```

实测（deepseek-chat，753 个 B 档 span）：

```text
LLM 作答 736（98%），正确率 80.7%，我们 73.2%
救 130 / 改坏 75 → 净 +55
全局 precision 92.5% → 93.1%，coverage 88.8% → 89.3%
分集：开发 95.2→95.8 · 留出 94.9→95.1 · 泛化 94.5→94.8 · 散文 74.9→76.9
```

置信度门槛无效（0.6→0.95，正确率只从 80.7% 到 82.9%），所以不设阈值。
默认关闭是因为评测要可复现，不该依赖外部服务。
```

## 4. 支柱三：出错不显眼

前提：用户不会去核对，所以要让他"即使遇到错误也不会被误导"。

### 4.1 视觉规范

```text
A 级  ruby 正常显示，颜色/字号与正文一致
B 级  ruby 正常显示，但整块加一条极淡的下划线（或降低 20% 不透明度）
C 级  不显示 ruby，正文完全不变
```

要点：

- **默认外观 = 没有假名**，所以 C 级不会显得"坏了"
- B 级的淡下划线是"可点"，不是"警告"
- 不要用问号、红色、感叹号——那会让用户去质疑整段内容

### 4.2 点词查候选（**已实现**，演示页可点）

B 档的片段在页面上有虚线下划线，点一下弹出候选列表（按语料频率排，系统选的那个在第一位）：

```text
床[ゆか]  ← 点击 → ゆか / しょう / とこ
```

选中后本行立刻改读音（只改这一句的显示，不写回词表）——**用户看上下文比我们准**。

页面顶部还有一块 **B 档校正面板**：把这一页所有 B 档词按词形聚合，点一次改全部出现。

```text
床   2 处   ゆか / しょう / とこ
頭   1 处   あたま / とう / かしら / …
```

为什么需要它：同一个词在一页里出现多次（`床` 两次、`何` 十几次），
逐个点太慢；而它们大概率读音相同，一次改完更合理。

面板默认折叠，展开后有「全部重置」：清掉本地记录、恢复原始读音。

**改动存在 `localStorage`**（键 `nihongo-acc:corrections:<页面标题>`），刷新后仍在；
不同文章分开存；存储不可用时自动降级（页面照常，只是记不住）。

### 4.3 自由编辑振假名（**未实现**）

允许直接输入假名覆盖，但必须过校验：只允许平假名（I3）、摩拉数 sanity（I7），
并标记来源 `user-corrected`。**不回写词表**——收集到队列，离线统计后再定。

理由：我们的前提是"不设人工复核"，用户修改是参考信号，不是规则来源。

### 4.4 点词查询（原设计，已由 §4.2 覆盖）

```text
点击任意汉字词 → 弹出：读音（假名）+ 候选 + 词性
```

§4.2 已经实现了"点开看候选并切换"；释义与置信度来源还没做（需要词典释义字段）。

### 4.5 可选的反馈通道（不作为正确性依赖）

```text
长按注音 → 「这个读音不对」→ 上报 {surface, 当前读音, 上下文, 版本}
```

纪律：

```text
1. 不做即时修改（避免误报污染数据）
2. 按 surface 聚合，人工批量看，进词表后随版本发布
3. 用户关闭反馈不影响任何功能
```

## 5. 系统架构

### 5.1 模块与接口（实际映射）

设计里的六个职责，落点（引擎在 `tools/annotate.py`，对外包一层 `nihongo_acc.py`）：

| 设计职责 | 实际实现 | 状态 |
|---|---|---|
| `normalize(text)` | 无（直接按 `\n` 切行） | ❌ 未做 NFKC/全角统一 |
| `tokenize(text)` | `get_tagger()` → Sudachi（mode A） | ✅ |
| `resolve(token)` | `occ_reading()` 取读音 + 查表（key 就是表层） | ✅ |
| `decide(candidates)` | `_word_decision()` 有序规则链（§3.3） | ✅（无 confidence） |
| `align(token, reading)` | `split_pieces()` 汉字块/假名块对齐 | ✅ |
| `emit(segments, format)` | `annotate()` 组装 `{lines, romaji, keys, stats}` | ✅ JSON |

模块边界在文件层面是"一个文件一组函数"，不是设计里那种独立模块；
拆成这样是因为判定链需要共享上下文（行文本、偏移、分词特征），
拆成独立模块反而要传一堆参数。

四条不变量（实现里都成立，`tests/` 有覆盖）：

```text
1. concat(segments.base) === 原文        —— 用 line.find(片段, pos) 逐段推进保证
2. ruby 非空 ⇒ base 至少含一个汉字        —— 假名块永远 K
3. ruby 只含假名（允许 ー）               —— occ_reading 只产出假名
4. 失败不抛异常                           —— 返回 C + 结构化 reason code
```

### 5.2 数据流

```text
原文（按 \n 切行）
 ├→ tokenize        Sudachi 分词
 ├→ occ_reading     取读音（Sudachi reading_form → 平假名）
 ├→ split_pieces    汉字块/假名块 DP 对齐
 ├→ _word_decision  6 条规则链 → source
 ├→ assign_level    source + 语料统计 → A / AB / B
 ├→ merge_counters  数字＋助数词
 ├→ apply_llm       只换 B 档（--llm）
 ├→ 不变量校验       违反即弃权
 └→ emit            {lines:[{text, segments[]}], stats}
 └→ 弃权段的 reason code 随响应返回（不展示给用户，用于统计与抽检）
```

"为什么"要保留（不显示给用户），用于日志与事后抽检。

### 5.3 部署形态：独立进程 + 多入口（stdio / 本地页面已实现，正式服务未做）

一个常驻进程，三种调用方式，同一套实现：

```text
                         ┌──────────────────────────┐
HTTP  :8787  ◄───────────┤                          │
stdio（嵌入式）◄──────────┤   annotator 进程          │──► Sudachi（mmap）
CLI  --batch ◄───────────┤   （Python，单实例）      │──► 词表 / 规则表 / 缓存
                         └──────────────────────────┘
```

| 入口 | 用途 | 备注 |
|---|---|---|
| `POST /v1/annotate`（本地或服务器） | 桌面应用、Web 前端、其他机器 | 默认只监听 127.0.0.1；对外要开 token |
| stdio（JSON Lines） | 打包进桌面应用时随应用启动 | 不用端口，不会被防火墙/端口冲突干扰 |
| `annotator --batch file.txt` | 离线批处理、评测脚本 | 与 HTTP 同一份代码路径 |

为什么是"独立进程"而不是库：

```text
1. 词典大、启动慢，进程常驻最划算；调用方重启不影响缓存与预热
2. 崩溃隔离：标注进程挂了，客户端降级为"不注"，不会拖垮主应用
3. 语言无关：Python 写得出来，任何客户端用 HTTP/stdio 都能接
4. 可远程：同一台服务器给多台机器/多个客户端共用
```

进程内约束（必须写死）：

```text
Sudachi 的 tokenizer 不是线程安全的 → 每个 worker 进程持有独立实例；
并发靠 worker 数，不靠线程；HTTP 层只做排队与超时
```

**请求**

```http

        { "base": "の曲",     "ruby": null, "level": "K" }
      ],
      "romaji": { "sing": "" },
      "keys":   { "ime": "" }
    }
  ],
  "stats": { "coverage": 0.75, "abstain": 1 }
}
```

五个级别（A / AB / B / C / K）：

| level | 含义 | ruby | 开发集 precision | 下游 ②③ |
|---|---|---|---|---|
| **A** | 语料证明单读 / 人工确认 | 有 | 96.2% | 参与 |
| **AB** | 多读，但读音是语料主读 | 有 | 91.7% | 参与 |
| **B** | 多读≠主读 / 专名 / 数字 | 有 | 73.4% | 参与 |
| **C** | 放弃，不注（只有 OOV / 对齐失败） | null | — | **跳过**（整行可能为空串） |
| **K** | 假名直通，本来就没有汉字可注 | null | — | 参与（按假名转写） |

一致性规则（实现时的硬约束）：

```text
1. ②③ 只能由 ① 的 ruby / K 段拼接，绝不由汉字直接转写
2. level = C 的段不进 ②③ —— 宁可整行罗马音残缺，也不给不敢担保的读音
3. 同一响应里三层必须互相一致：同一个读音、同一套切分
```

K 这一级容易被漏掉：`は`、`が`、`る` 本来就没有汉字，它们不是"放弃"，
而是"没有可注的东西"，必须参与罗马音与键位的生成。上例里 `wa`、`ga`、`ru` 都来自 K 段。

**错误与降级**（都是"宁可少标"的实现）

| 情况 | 返回 | 客户端表现 |
|---|---|---|
| 文本为空 | 400 | 不标注 |
| 超长（>5000 字） | 413 + 允许的最大长度 | 客户端切段重试 |
| 词典仍在加载 | 503 + `retry-after` | 整段 C 级 |
| 单段超时 | 200，该段 `level: C`, `reason: "timeout"` | 静默不标 |
| LLM 不可用 | 200，多音词降为 C | 静默不标 |
| 内部异常 | 500 + `requestId` | 整段 C 级，不重试 |

**stdio 实际行为**（与上表的对应关系）：

```text
坏 JSON      → {"error": "bad json: ..."}，进程不退出，继续服务下一行
内部异常     → {"error": "<异常类型>: <消息>", "version": {...}, "lines": []}
空文本       → {"lines": [{"text": "", "segments": []}], "stats": {...}}
无 HTTP 状态码——以上都是单行响应里的 error 字段
```

设计纪律：**只有"请求本身不合法"才报错；"标不出来"是正常结果，不是错误。**

### 5.5 缓存分层

设计三层，**当前只实现了一层**：

```text
LLM 选择缓存     ✅ data/cache/llm/choices.json
                 key = sha1(行文本 + 位置 + 词形 + 候选集)
行级 LRU         ❌ 未实现
歌曲/文档级       ❌ 未实现（D3：本版不做）
```

实测单行 0.4ms，缓存收益有限，所以没做。
缓存只影响速度，不影响正确性；LLM 缓存的 key 含候选集，词表变了自然失效。

## 7. 罗马音与键盘输入层（**已实现**）

同一份假名，两种用途，**两套规则，不能混用**（实现在 `nihonco_yomi/romaji.py`）。

| 用途 | は（助詞） | を | へ | 長音 | っ | ん（元音前） |
|---|---|---|---|---|---|---|
| 唱歌/朗读转写 | wa | o | e | kyō | kko | n |
| 显示用 Hepburn | wa | o | e | kyō | kko | n |
| IME 键位 | ha | wo | he | kyou | kko（ch/ts 前 t） | n' |

一句三写：

```text
原文     今日は雨が降る
振假名   今日(きょう)は 雨(あめ)が 降(ふ)る
唱歌     kyō wa ame ga furu
键位     kyou ha ame ga furu
```

### 7.0 已定的口径

| 问题 | 决定 |
|---|---|
| 长音 | **完全逐字转写**：`きょう → kyou`、`とうきょう → toukyou`、`ひろう → hirou`、`コーヒー → ko-hi-` |
| 分词 | 按 Sudachi 的词分段（空格） |
| ぢ / づ | 现代音：`ji` / `zu` |
| ん 的撇号 | **只有键位层**加（`shin'ichi`），罗马音写 `shinichi` |
| 助詞 は/へ/を | **严格按 POS**：只有 POS 带「助詞」才读 wa/e/o |
| 连写 | 助動詞/接頭辞 贴前词（ikiteru、onegatte）；助詞 一律分开 |
| 标点 | 保留原句标点：开括号贴后词、闭括号与句末贴前词、句末后加空格 |

长音风格目前只有一种：**逐字**（`コーヒー → ko-hi-`）。预留一个开关没实现：

```text
--romaji-style orthographic   （当前，唯一的实现）  コーヒー → ko-hi-、きょう → kyou
--romaji-style phonetic       （预留）              コーヒー → koohii、きょう → kyoo
```

预留的理由：`ko-hi-` 对"不懂日语但想跟着念"的读者可能不友好（会读成 "ko hi"）。
真有人反馈时再加，不在 v1 引入第二个需要测的维度。

### 7.1 键位层的规则

```text
表驱动     基础 / 拗音 / 外来语 / 稀有（ぢ→di、づ→du、ぢゃ→dya、词尾っ→xtsu）
四条规则   长匹配优先；っ双写（ch/ts 前 t）；ん在元音/や行前加 '；ー写 -
选写法     取所有主流 IME 都接受的写法，优先最短（shi 而非 si）
```

三个跨片段的处理（实现里踩过）：

```text
っ 跨 token      降っ + て 是两个 token；"っ" 的叠辅音要看下一个 token 的首假名
                 → 以 っ 结尾的组并进下一组，再做转换（futte，不是 futsu-te）
助動詞 贴前词     判据是"前面是不是谓语"，不是白名单：
                 前一片段 POS 含 動詞/形容詞 → 贴（生きてる → ikiteru、飲んだ → nonda）
                 接终止形的单独成词 → 不贴（晴れる でしょう → hareru deshou）
接頭辞           お / ご 仍与后面的词分开（お 願って → o negatte）
```

### 7.2 怎么验证（无真实 IME 可调）

```text
1. 表覆盖审计   语料里所有假名单元必须能在表中找到
                 → 已跑：102144 个单元，零缺口
2. 往返测试     tests/test_romaji.py 里有独立的贪心解析器，
                断言 解析(生成(kana)) === kana
3. fixture      56 条单测覆盖 ん/っ/ぢ/づ/小写假名/ー/助詞
4. 人工确认     只在发布前做一次：真机 IME 打一遍 fixture
```

纪律：**用于校验的模拟器，其"可接受写法"必须独立于生成器**，否则是自证。

### 7.2.1 输出

```bash
python tools/annotate.py --text "東京でコーヒーを飲んだ" --layers ruby,romaji,keys
```

```text
R  toukyou de ko-hi- o nonda
K  toukyou de ko-hi- wo nonda
```

片段上也挂了 `romaji` / `keys` 字段；整行按词用空格连接。

### 7.3 与振假名的关系

```text
振假名是上游：先确定读音（kana），才能生成罗马音与键位
所以罗马音层的错误不会反过来影响注音；但注音错 → 罗马音一定错
```

## 8. 实时 / 非实时两档

### 8.1 非实时（默认）

```text
整首/整篇跑完 → 展示
允许：三家分析器投票 + LLM 消歧
延迟：整首 0.3–2s
```

### 8.2 实时（可选）

```text
预热常驻 + 分级：
  ① 缓存命中 → 直接返回
  ② 单分析器 + 词表（覆盖 ~90%）→ 2–4ms/行
  ③ 只有歧义 token 才追加投票 / LLM  → +1–3ms
  ④ 仍不确定 → C 级（不标）
预取：当前行展示时，后台已算完下两行
两段式：即时段保守；后台精修结果到达后，若用户还没读到该行则替换
```

### 8.3 实时场景的硬规则

```text
单段超时       300ms → 该段直接 C，不重试
积压处理       丢弃旧行，不补标已经过去的内容
错位禁止       宁可没有假名，也不要晚到的假名
降级顺序       精修 → 投票 → 单分析器 → 不标
```

## 9. 资源预算（实测值，2026-11）

单 worker 进程，MacBook（Apple Silicon）：

| 项 | 设计预估 | 实测 |
|---|---|---|
| 词典 | 私有 100–200MB | sudachidict_core 193MB（mmap） |
| 启动（冷） | 0.5–1.5s | **0.18s** |
| 单行延迟（热） | 1–3ms | **0.4ms**（600 行 233ms） |
| 整首 40 行 | 40–120ms | **约 16ms** |
| 表内存 | 5–10MB | 默认只载 heteronym 0.2MB + stats 0.14MB；`--llm` 另加 readings 8.7MB |

部署建议（未验证，属设计）：

```text
单机单 worker        够用；按 0.4ms/行算，QPS 远高于 10–20
多 worker            每进程一份 Sudachi；词典 mmap 共享，内存增量小
与业务同机            省一次网络往返
```

内存纪律：**不要在请求处理中把整本词典复制进堆**——Sudachi 用 mmap，词典页是文件支持的。

## 11. 风险与待解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 金标准语料偏文学 | 歌词场景实测更差 | 自建歌词评测集，单独看指标 |
| 词表冷启动覆盖低 | 首版体验一般 | 先发高频词表，逐版本补 |
| LLM 编造读音 | 用户被误导 | 只做选择 + 与词典交叉 |
| 固有名詞读音不准 | 误标（73.8% 正确） | 标 B 档淡色；进词表后升 A |
| 实时压不准 | 掉行 | 预取 + 两段式 + 丢弃策略 |
| 用户上报噪声 | 污染词表 | 聚合后人工批量确认，不即时生效 |
| **服务成为单点** | 挂了全端不可用 | 客户端本地降级（整段不标）；进程崩溃自动重启 |
| **词典升级改变输出** | 客户端缓存与显示不一致 | 响应带 version，客户端按版本失效 |
| **对外暴露被滥用** | 被当成免费 API 刷 | 默认只听 127.0.0.1；对外强制 token + 限流 |

待解：

```text
1. 并发模型：单 worker + 排队，还是每核一个 worker？先按单 worker 上线，量到瓶颈再加
2. LLM 的位置：在标注进程内调用，还是客户端调完把候选回传？前者简单，后者省服务端成本
3. 词典版本与规则版本如何冻结：两者都进响应 version，还是合并成一个 release id？
4. 远程部署时的隐私：歌词文本会经过服务器，是否要提供"本地模式"（同进程 stdio）给在意的人
```
