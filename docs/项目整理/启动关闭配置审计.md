# 启动 / 关闭 / 配置 / 日志审计

> 不含数据目录迁移。

## 0. 结论

```text
启动主链路可用
配置写入原子且有文件锁
发现一个会破坏用户配置的损坏恢复问题
关闭路径没有统一 flush / cleanup
```

## 1. P1：损坏的 data/config.json 会被静默覆盖

启动时：

```python
def _load(path):
    try: return json.loads(...)
    except Exception: return {}
```

损坏配置被当作空对象，直接使用默认值，没有提示。

之后用户切主题/播放模式：

```python
d = FS.read_json(FILE, {}) or {}
player = d.setdefault("player", {})
ui = player.setdefault("ui", {})
ui["theme"] = ...
```

结果：

```text
损坏的 config.json
→ 被读成 {}
→ 只写回 player.ui
→ 原文件其他配置全部丢失
```

需要：

```text
损坏时备份为 config.json.bad
提示用户
再写默认配置
```

已实现 JSON 语法、顶层对象和已知嵌套结构的校验；
结构不符合 defaults 时按损坏处理：

```text
config.json.bad-YYYYmmdd-HHMMSS
→ 使用默认配置
→ warning 提示
```

覆盖的嵌套示例：

```text
player 不是对象
player.ui 不是对象
lyrics 不是数组/对象
delta_tiers 不是 3 元素数组
window_min 不是 2 元素数组
library.extensions 不是数组
```

## 2. P2：关闭应用没有统一 flush / cleanup — 已修复（最小版）

当前关闭流程：

```text
窗口关闭 → hide
应用退出 → webview.start 返回
```

没有：

```text
通知前端 flush 歌词
等待保存完成
取消语音分离任务
shutdown HTTP server
清理子进程
```

风险：

```text
未保存歌词丢失
demucs 子进程残留
后台线程在退出时被直接杀掉
```

## 3. P2：启动失败没有用户可见提示 — 已修复（最小版）

`main` 中：

```text
bootstrap
logsetup
LIB.load_cache_for_playlists
VOC.cleanup
make_server
webview.start
```

其中任何一步失败：

```text
进程退出 / 异常
用户只看到窗口没打开
```

`sys.excepthook` 只能写日志，不能提示启动失败。

已加入：

```text
main 捕获启动异常
→ stderr 打印 traceback
→ NSAlert 显示“桃歌启动失败”
→ 显示异常摘要和日志路径
→ 重新抛出，保持非零退出
```

日志初始化失败不再阻止启动，只退化为 stderr。

## 4. P2：多实例没有互斥 — 已修复

没有单实例锁：

```text
两个 app 进程
→ 同一个 data 目录
→ 启动时 VOC.cleanup 可能删掉另一个实例正在用的缓存
→ 配置/索引写入竞争
```

文件锁只保护单文件写入，不保护“整个应用实例”。

已加入：

```text
data/app.lock
fcntl.flock(LOCK_EX | LOCK_NB)
启动前抢锁
第二个实例提示“桃歌已经在运行”
进程退出时内核自动释放
```

## 5. P3：日志初始化失败会阻止启动 — 已修复

`logsetup.setup()` 直接：

```text
mkdir CACHE
open app.log
```

失败时应用启动失败，没有退化到只写 stderr。

已改为：日志初始化失败只打印 stderr，继续启动。

## 6. P3：日志轮转不保留历史 — 已修复

只保留：

```text
app.log
app.log.1
```

旧 `.1` 被覆盖。不是数据问题，但排障时可能丢上下文。

已改为：

```text
app.log + app.log.1..3
app.log_keep_files 默认 3
启动时和运行中超过 log_max_bytes 都轮转
退出时同时取消 jobs / vocals / soundtouch 子进程
```

## 7. 已确认正常

```text
atomic_write_text 同目录临时文件 + fsync + replace
user_config 读写有文件锁
主题/播放模式走同一配置文件
启动时创建 frozen 用户目录
日志 Tee 到 stdout/stderr
默认配置只来自 config/defaults.json
```

## 8. 建议顺序

```text
P1 config 损坏备份与提示
P2 关闭前 flush / 任务清理
P2 启动失败弹窗
P2 单实例锁
P3 日志初始化降级
```

测试基线：

```text
401 Python
87 前端
UI 冒烟通过
```

## 9. 复核：单实例、日志与退出

已确认：

```text
配置嵌套结构校验
配置损坏备份
Cmd+Q 前 flush
启动失败原生提示
单实例锁
日志多份轮转
日志初始化失败不阻止启动
```

### P3：单实例锁获取晚于日志初始化 — 已修复

当前顺序：

```text
logsetup.setup()
→ 写启动日志/轮转
→ _acquire_instance_lock()
```

第二个实例会先写日志，再发现已有实例退出。

影响：

```text
第一个实例的 app.log 可能被第二个实例轮转
日志被拆到旧文件/新文件
```

已改为：

```text
启动第一件事抢 app.lock
失败直接提示退出
成功后再初始化日志
```

### P3：窗口关闭按钮不 flush — 已修复

当前：

```text
窗口关闭 → hide
Cmd+Q → prepareShutdown
```

这是刻意保留后台播放的设计。
但如果用户关闭窗口后应用崩溃，仍可能丢失最后一个 autosave 周期内的草稿。

已改为：

```text
窗口关闭 → 后台线程调 prepareBackgroundFlush()
→ 隐藏窗口
→ 冲突状态不弹窗，保留草稿
```

### P3：prepareShutdown 没等待 saveOpen — 已修复

```js
if(ok && NH.saveOpen) await NH.saveOpen();
```

`saveOpen` 现在返回请求 Promise，`prepareShutdown` 会等待它。

歌单打开状态可在退出前写入。

### P3：日志文件异常被静默吞掉 — 已修复

`_LogSink.write` 和 `_rotate` 的异常都被吞掉。

效果：

```text
日志可能停止记录
应用继续运行
```

建议至少记录一次 stderr 警告。

### P3：配置只校验类型，不校验范围 — 已修复

例如：

```text
http.timeout_s = -1
jobs.max_active = 0
vocals.max_bytes = -1
```

类型正确但语义无效。

可在校验层补最小值。

## 10. 再复核

已确认：

```text
单实例锁先于日志初始化
窗口隐藏时后台 flush
prepareShutdown 等待 saveOpen
日志异常 stderr 警告
配置范围最小值校验
```

### 剩余低优先级

#### P3：后台隐藏 flush 没有可见结果

```text
窗口关闭 → 后台 flush
```

如果保存失败：

```text
窗口已经隐藏
用户看不到失败提示
```

冲突状态则直接跳过 flush，保留草稿。  
这是有意的静默行为，但用户可能不知道需要重新打开窗口处理。

#### P3：范围校验只覆盖部分键

例如：

```text
player.ui.autosave_ms
player.speed_min / max / step
vocals.ratio_min
waveform.rate / step
```

仍只校验类型，不校验合理范围。

#### P3：日志警告只报一次

`_LogSink._warn` 只输出第一次错误。

优点是避免刷屏；  
缺点是日志后续恢复/再次失败没有状态变化提示。
