# 歌词编辑器保存/备份/恢复审计

> 范围：保存、自动保存、flush、替换、恢复、删除、草稿状态。
> 只审计，不修改。

## 0. 结论

```text
主保存路径有锁和 revision 校验
自动保存/手动保存基本闭环
发现一个可能导致草稿丢失的替换路径
```

## 1. 正常保存

`saveLrc`：

```text
等待 SAVE_PENDING
检查 EDIRTY / force
记录 EDIT_REVISION
读取当前 EROWS
调用 /api/lrc
```

成功时：

```text
更新 LRC_VERSION
revision 未变 → merge ids + EDIRTY=false
revision 已变 → 保持 dirty
```

失败：

```text
不清除 dirty
如果非 silent 提示
```

这是正确的。

## 2. 自动保存

`markDirty`：

```text
EDIT_REVISION++
EDIRTY=true
重置 autosave timer
1.5s 后 saveLrc(true)
```

`setLrcLocked(true)` 会清理 timer，  
离开编辑器前应由 `flushLrc` 保存。

## 3. P1：replaceLrc 不检查 pending save 的结果 — 已修复

`replaceLrc`：

```js
if(NH.SAVE_PENDING) await NH.SAVE_PENDING;
const r=await NH.api(...replace/restore...);
```

如果前一次保存：

```text
返回 false
仍然存在未保存草稿
```

`replaceLrc` 仍会继续覆盖。

恢复/导入本身是显式覆盖，但这里至少应该：

```text
如果 pending save 失败
→ 不继续覆盖
→ 保留草稿
→ 提示用户重试或明确确认丢弃
```

已改为：

```text
设置 LRC_REPLACING + LRC_FLUSHING
→ 阻止切歌，但允许覆盖前的保存
→ saveBeforeReplace()
→ 失败则取消 replace
```

## 4. P2：lrcreset / 导入走同一路径

恢复和导入都调用 `replaceLrc`，因此继承上面的问题。

确认框确实提示“当前编辑内容会丢失”，  
但“保存失败”不应该等同于“用户确认覆盖”。

## 5. P2：删除歌词不检查 dirty — 已修复

`lrcfiledel` 只等待 `SAVE_PENDING`：

```js
if(NH.SAVE_PENDING && !await NH.SAVE_PENDING) ...
```

如果：

```text
EDIRTY=true
autosave timer 还没触发
SAVE_PENDING=null
```

删除会直接执行，未保存草稿丢失。

已改为：

```text
删除前同样 saveBeforeReplace()
保存失败则取消删除
```

## 6. P2：openLrcEditor 直接清 dirty — 已修复

打开编辑器后：

```js
NH.EDIRTY=false;
```

没有检查是否还有 pending save。

如果调用时存在未完成的保存：

```text
旧保存完成后 revision 可能变化
新编辑器已经加载
```

已改为：

```text
openLrcEditor 发现 EDIRTY 或 SAVE_PENDING
→ 先 flushLrc()
→ 失败直接返回
→ 不请求文档、不重建 EROWS、不清 dirty
```

`resetall` 也改为只有在 `load` 成功后才重新打开编辑器。

## 7. 已确认正常

```text
保存失败保留 dirty
版本冲突 409 保留草稿
revision 变化不误清 dirty
SAVE_PENDING 串行化
恢复/删除有版本参数
首次保存备份
切歌前 flush
```

## 10. 复核：版本冲突后的退出路径

### P2：保存冲突后无法正常离开编辑器 — 已修复

当 `saveLrc` 收到 409：

```text
EDIRTY 保持 true
LRC_VERSION 仍是旧版本
```

接下来：

```text
切歌
切回普通页
打开编辑器
```

都会先尝试 flush，再次收到 409，返回失败。

结果：

```text
草稿不会丢
但用户被卡在 LRC 模式
只能刷新整个应用
```

已加入冲突选择：

```text
重新加载服务端
→ 放弃本地草稿，重新读取

用本地覆盖
→ 先读取服务端最新 version
→ 再用本地 EROWS 保存

取消
→ 保留草稿，留在编辑器
```

冲突时暂停自动保存，避免反复重试。

## 11. 冲突处理后的复核

冲突选择已实现：

```text
重新加载服务端
用本地覆盖
取消
```

### P3：openLrcEditor 请求期间仍可编辑 — 已修复

`openLrcEditor` 先 flush，再请求 `/api/lrc`；请求返回后重建 EROWS。

冲突选择“重新加载服务端”时，编辑器没有锁定，  
用户在请求期间仍能输入；响应回来后：

```text
EROWS 被服务端文档覆盖
EDIRTY=false
```

就会丢掉这段新输入。

已改为：

```text
请求前记录 EDIT_REVISION
响应回来发现已变化
→ 丢弃服务端响应
→ 保留当前 EROWS / dirty
```

### P3：冲突弹窗按 Enter 会执行“用本地覆盖” — 已修复

`openDialog` 的全局 Enter 处理固定返回 true：

```js
finish(input ? ... : true)
```

如果焦点在额外的“重新加载服务端”按钮上，按 Enter 仍会走本地覆盖。

已改为：

```text
焦点在“重新加载服务端” → Enter 执行重新加载
焦点在“取消” → Enter 取消
其余 → Enter 执行主按钮
```

### P3：reloadLrcFromServer 不检查 openLrcEditor 结果 — 已修复

`reloadLrcFromServer(true)` 调 `openLrcEditor` 后直接返回 true。  
如果加载失败，调用方会认为冲突已解决。

已改为返回实际加载结果，并捕获加载失败。
