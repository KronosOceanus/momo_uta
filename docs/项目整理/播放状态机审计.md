# 播放状态机与异步播放边界审计

> 范围：AudioEngine、load、seek、单句循环、切歌、匹配完成后的刷新。
> 只审计，不修改。

## 0. 结论

```text
播放主链路可用
本轮 P1/P2 已修
查看歌曲与播放歌曲已分离
```

## 1. nextIdx 在“当前不在任何歌词行”时少走一格 — 已修复

当前：

```js
let at = items.findIndex(x => x.i === i);
if (at < 0) {
  at = dir > 0 ? items.findIndex(x => x.t > t) : items.length - 1;
}
const to = at + (dir > 0 ? 1 : -1);
```

如果当前时间在第一句之前：

```text
dir > 0
at = 第一句的 index
to = at + 1
→ 直接跳到第二句
```

如果当前时间在最后一句之后：

```text
dir > 0
at 找不到
at = items.length - 1
to = items.length
→ 返回 items[at]，最后一句
```

结果：

```text
下一句跳过第一句
末尾下一句不前进
```

上一句也有类似偏移。

## 2. 旧 seek 可能在切歌后操作新歌 — 已修复

`seekPrecise` 只检查：

```js
NH.isCurrent('seek', seq)
```

不检查：

```text
当前歌曲 uid
commitAudio 是否已经切到别的歌
```

场景：

```text
A 播放中
→ seek A 的某一句
→ 立刻切到 B
→ A 的 seek await 返回
→ 继续执行 NH.au.currentTime = A 的时间
```

此时 `NH.au` 已经是 B。

## 3. playLine 在 await 后无条件播放 — 已修复

```js
async function playLine(i){
  ...
  await seekPrecise(...);
  await NH.au.play().catch(()=>{});
  highlight(i);
}
```

如果 await 期间：

```text
用户切歌
用户再次双击另一行
seek 被新的 seek 取代
```

旧 `playLine` 返回后仍会：

```text
play 当前音频
高亮旧行
```

需要一个 play/seek 请求 token 或 song uid 校验。

## 4. SEEK_ACTIVE 在提前返回时可能残留 — 已修复

```js
if(!NH.isCurrent('seek',seq)) return;
...
NH.SEEK_ACTIVE=false;
```

如果旧 seek 因为被新 seek 取代而提前返回，  
`SEEK_ACTIVE` 留给新 seek 处理是合理的。

但如果新的 seek 也没有跑完：

```text
旧 seek 提前返回
新 seek 又因为切歌/异常提前返回
→ SEEK_ACTIVE 永久为 true
```

下一次 seek 会错误复用旧的 `SEEK_WAS_PLAYING`。

## 5. seekIdx 的 keepPlaying 参数未使用 — 已删除

```js
function seekIdx(i, keepPlaying){
  ...
  seekPrecise(t);   // 是否续播由 seekPrecise 自己判断
}
```

参数存在但没用，容易让调用方误以为可以强制保持播放状态。

## 6. 播放中匹配完成

之前修过：

```text
匹配完成 → load(d.uid, false)
→ 不重绑音频
→ 不重置 currentTime
```

这次审计确认该路径仍然正确。

## 7. 单曲循环 ended

```js
const song = NH.S;
setTimeout(() => {
  if(!song || NH.S !== song || !NH.loopSong) return;
  NH.au.currentTime = 0;
  NH.au.play();
}, 0);
```

有 `NH.S !== song` 校验，切歌后不会重启旧歌。
