## 4.1 运行时发现：缓存歌词仍显示“无词”

状态：已修复。

`_entry` 的索引命中分支调用：

```python
_has_lyric(*LY.split_name(...), ...)
```

但 `split_name()` 返回顺序是：

```text
(artist, title)
```

而 `_has_lyric()` 需要：

```text
(title, artist)
```

参数反了，缓存查找 key 错误，于是：

```text
只有 nhlrc → 有词
只有歌词缓存 → 无词
```

修复后按正确顺序传参，缓存歌词也会让曲库标记为有词。

## 5. 发现的问题

### P1：索引路径对应到另一个 uid 时会静默丢歌

状态：已修复。

`load_for_playlists` 现在校验 `_entry` 返回的 uid；不匹配就跳过并重新计算 missing。

`load_for_playlists` 先按 uid 选路径：

```python
chosen[uid] = p
```

后面：

```python
e = _entry(p, ...)
if e and e["file"] not in seen:
    out.append(e)
```

没有检查：

```text
e["uid"] == uid
```

如果文件被替换、重打标签，指纹从 uid A 变成 uid B：

```text
索引仍给 uid A → 路径 p
_entry(p) 返回 uid B
out 里加入了 uid B
missing = wanted - set(chosen) 仍为空
```

结果：

```text
播放列表引用 A
实际曲库只有 B
A 被视为“没有缺失”
```

这会让一首歌悄悄从歌单里消失，且不触发缺失提示。

建议：

```text
按 uid 取路径后，必须校验 _entry 返回的 uid
不匹配 → 记入 missing，触发重建
```

### P2：LRC 配对可能误配

状态：已修复。

现在按层级配对：同目录精确 → 全局精确 → 同目录归一化 → 全局归一化；
只有明确唯一才配对，多候选进入 ambiguous/pending。

`_stem_key` 会去掉：

```text
数字前缀
符号
部分括号后缀
```

如果同目录有：

```text
01 Song.mp3
Song.mp3
Song.lrc
```

可能把同一个 LRC 配给错误的音频。

同目录“唯一 LRC”兜底也会在没有同名匹配时配对唯一 LRC。

建议审计或增加：

```text
文件名完全匹配优先
归一化匹配只作为次选
同目录唯一 LRC 增加确认/记录
```

### P2：异常导入可能没有反馈

状态：已修复。

`import_text` 返回失败或抛异常时，音频仍加入 `added/pending`，并返回 `failed`。

`import_paths` 中：

```text
valid_import 通过
LRC.import_text 返回 ok:false
```

音频既没有进入 `added`，也没有进入 `pending`，只表现为少了一首。

现在：

```text
音频加入 added/pending
failed = [{audio, lrc, error}]
failed_count
```

前端 toast 显示失败数量。

### P2：歌单 JSON 坏结构可能崩溃

状态：已修复。

`playlists.load` 现在逐层清洗；坏 lists/members/list_order/open 条目丢弃，不影响正常歌单。

`playlists.load`：

```python
out["lists"] = [x for x in d.get("lists", []) if x.get("id") and x.get("name")]
out["members"] = {k: list(v) for k, v in d.get("members", {}).items()}
```

如果 `lists` 里不是对象，或 `members` 里不是数组：

```text
AttributeError / TypeError
```

这是“坏数据直接丢弃”原则之外的情况。

### P2：导入后加入歌单和加入曲库不是原子操作

状态：已修复。

现在先确认歌单存在，再以曲库实际存在的 uid 为准加入歌单；不接受未进入 CACHE 的 uid。

`import_to_list`：

```text
LIB.add_paths()
PL.add(lid, uids)
```

`uids` 来自 `res["added"]`，不是来自 `add_paths` 的结果。

如果文件在两步之间消失，或 `add_paths` 拒绝：

```text
歌单新增了 uid
曲库没有对应条目
```

会留下一个立即缺失的歌单成员。

### P3：删除/移动文件后索引不会立刻裁剪

状态：已修复。

`load_for_playlists` 会收集 wanted uid 下不存在的索引路径，调用
`LI.prune_paths()` / `FP.prune_paths()` 定向清理；`imports.json` 仍保留，不自动删。
`refresh()` 在 uid 变化时把旧 uid 加入 `LAST_MISSING`。

### P3：重复音频清理后 imports.json 仍可能保留旧路径

状态：按决定保留。

imports.json 是导入历史，不自动清理。

清理重复音频只移动文件，不改：

```text
data/curated/imports.json
```

旧路径仍留在导入历史里，`load_imports` 会跳过不存在文件，但记录不会自动清理。

## 6. 已确认闭环


```text

2. ✅ 导入失败返回 failed / pending
3. ✅ 歌单 JSON 坏结构丢弃
```

## 11. 第三轮复核

主链路没有新的致命问题。发现两个残留点。

### P2：imports.json 没有结构清洗 — 已修复

`load_imports()` 直接返回 `json.loads()`：

```python
return json.loads(IMPORTS.read_text(...))
```

如果文件是：

```json
{"audio": "x"}
```

或数组里包含 `null` / 字符串，后面会出现：

```text
scan_library: row["audio"] → KeyError
save_import: r.get() → AttributeError
load_for_playlists: row.get() → AttributeError
_resolve_uid: row.get() → AttributeError
```

这和之前的 playlists.json 问题同类，但 imports.json 还没有清洗。

现在：

```text
顶层不是数组 → []
每行不是对象 → 丢弃
audio 不是非空字符串 → 丢弃
重复 audio → 去重
```

### P3：单曲 move 不校验源歌单成员 — 已修复

`move_many` 会先过滤：

```python
moved = [u for u in moved if u in src]
```

但 `move()` 没有：

```python
d["members"][lid_from] = [u for u in ... if u != uid]
seq = d["members"].setdefault(lid_to, [])
if uid not in seq: seq.append(uid)
```

现在 uid 不在源歌单时直接返回，不再注入目标歌单。

### P3：load_for_playlists 的 imports 二次补查 — 已修复

uid 校验失败后：

```text
initial chosen 有路径
→ 第一次 imports 补查没触发
→ _entry uid 不匹配
→ 重新计算 missing
```

现在 uid 校验失败、重新算出 missing 后，会再补查一次 imports，并重新收集条目。
